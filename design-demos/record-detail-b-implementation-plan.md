# 记录明细 B 方案实施计划

## 目标与范围

以已确认的第二版 B「一页账目」为视觉依据，以实际进入的可编辑收入和支出明细为主要范围，同时保持只读详情一致；修复备注提示对齐，优化编辑页既有时间信息。保留 OurNest 暖红、浅暖背景、无阴影及现有导航与公共组件规范。设计稿是视觉参考，不改变既有业务含义。

## 落地步骤

1. **收支明细**：可编辑页与只读页都以左对齐金额为视觉焦点，以连续分区和清晰行间距组织现有字段；可编辑页保留分类重选、金额键盘、日期、账户、家庭归属、保存和删除，新建快捷记账保持原样。保留收支差异、共享账本条件字段、空值、加载/错误/就绪状态和底部操作权限。长备注与长名称可换行，不遮挡操作或安全区。只读详情仅重组已有信息，不新增创建或更新时间，缺少父分类时不显示“未分类”。
2. **备注输入**：核对共享表单各调用场景，调整标签、提示和输入内容的对齐及多行布局；不修改数据接口或服务端契约，确认空值、已填、换行和接近 100 字时不溢出。实际设备字体与 textarea 渲染须手工核对。
3. **时间呈现**：保留既有创建时间和更新时间来源与本地时间格式；将不能证明人工编辑的“编辑于”调整为“最近更新”，对缺失或非法时间沿用现有安全处理，不增加审计含义。
4. **回归验证**：运行针对性测试，以及 `npm run verify`、`npm run ui:check`、`npm run visual:check`；检查收入/支出、个人/共享账本、备注与时间缺失、长文本、访客及不同角色操作边界。自动检查不能替代微信开发者工具和真机核验。

## 边界与回滚

不修改云函数、数据库字段、权限判定、路由或服务协议，不接触无关工作区改动。若视觉或交互回归，回退本次详情页和表单的相关改动即可；不涉及数据迁移、云部署或生产写入。

## 验收标准

- 金额及字段按 B 方案形成左对齐清晰层级；现有条件字段、内容和操作不丢失。
- 备注标签与输入/提示呈现协调，不因长内容遮挡；不改变原有保存行为。
- 创建时间与最近更新时间语义准确，缺失数据不显示虚构时间。
- 自动检查结果明确记录；开发者工具、不同设备尺寸与真实角色的手工验证单独标记，不把未执行的验证当作通过。
