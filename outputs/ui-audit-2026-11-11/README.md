# OurNest UI、交互与图表设计分析

审查日期：2026-11-11；源码基点：8da100c。覆盖 21 个注册页面、4 个主 Tab、20 个 tl- 业务组件。

[打开交互式 HTML 报告](./index.html) · [查看结构化证据](./evidence.json)

## 核心判断

OurNest 已有明确的暖红品牌、小窝 Logo、浅暖背景、线性图标和公共组件体系，适合针对性打磨。当前优先事项是保证图表数据口径、加载反馈、功能可达性和记录纠错闭环；无需为了去除 AI 感推翻品牌与布局。

本轮为源码审查、局部计算复现与交互示意，没有当前微信模拟器截图和真机性能证据。HTML 的手机结构和图表使用合成数据，不能当作当前实机截图或已实施改造。未修改业务代码。

## 图表重点

- 周 / 月 / 年实际采用 WXML 柱形看板。月度是近 6 个月，不是每日走势。自定义 / 累计使用 ECharts 三线趋势。不能把源码中保留的未挂载选项当作当前页面。
- 累计收入环图仍固定读取支出 categoryChart，且受支出 categories.length 控制；收入分类排行则读取 incomeCategories。图与列表可能口径矛盾。
- 1 元相对 1000 元应为 0.1% 柱高，当前算法最低绘制 4%，放大 40 倍。柱高应忠于数值，点击区域独立扩大。
- 本月未结束与前几个月完整月并排比较，需要显式标注完整度；平均应说明是月均还是日均，且是否包含当前部分期。
- 点击周柱跳明细，点击月柱切换整页月份，点击年柱先选中。建议统一点选反馈和明确的查看入口。
- Top 5 + 其余分类已经实现，应保留；分类颜色与图例稳定对应，弱化排名装饰色，小屏长标签另行验收。
- 共享统计保留付款人、消费归属、录入人三个口径；公共及多人按录入人展示，不在本轮自行改业务规则。

## 问题与建议

### F01 [P1] 累计切到收入，环图仍画支出

状态：已确认；领域：图表。

收入排行读取 incomeCategories，但累计环图固定请求 category，仍读取 categoryChart；挂载条件又依赖支出 categories.length。收入排行与环图可能相互矛盾，纯收入账本还可能没有环图。

影响：用户可能把支出结构当成收入来源，属于数据解释错误。

建议：环图、列表、标题和点击明细统一从 analysisType 选择数据。收入为空 / 支出为空分别判断，不用另一方向决定是否挂载。

验收：合成“收入仅工资 6000、支出仅餐饮 1200”与纯收入两组数据；切换后环图和列表金额、分类、总额完全一致。

依据：miniprogram/components/tl-tab-analysis/index.js:205；miniprogram/components/tl-tab-analysis/index.wxml:300；miniprogram/components/tl-tab-analysis/index.js:897

### F02 [P1] 第二次加载缺少可见反馈，可能出现空白

状态：已确认；领域：交互。

骨架只在 loading && !chartFirstReadyEver 时出现；第一次成功后再次请求，内容仍被 visibility:hidden 隐藏，没有同级刷新提示。网络等待期间会出现“控制栏还在、内容不见了”的状态。

影响：用户难以区分加载、内容丢失和渲染失败，容易反复点击。

建议：保持旧图表实例的生命周期策略；显示明确的刷新占位或加载层，禁止旧内容交互。切换新日期时显示新上下文的加载状态。

验收：首次加载、切换月份、切换收入、保存返回、请求失败都能看到唯一明确状态；不出现可交互的过期数据。

依据：miniprogram/components/tl-tab-analysis/index.wxml:43

### F03 [P1] 小额支出被最低柱高放大

状态：已复现；领域：图表。

dashboard.js 给所有非零柱设置至少 4% 高度，并四舍五入为整数百分比。最大 1000 元时，1 元应为 0.1%，实现却为 4%，图形比例放大 40 倍。

影响：小额和大额消费的视觉差距失真，影响趋势判断。

建议：数据柱保持真实比例和小数精度；单独为整列设置触摸区域。极小值用数值提示或细线表达，不改变柱高。

验收：用 0、1、20、1000 元验证比例；1 元柱保持 0.1%，整列触摸区仍充足，0 不绘制假柱。

依据：miniprogram/components/tl-tab-analysis/dashboard.js:141

### F04 [P1] 账单导入有页面和处理函数，但缺少可见入口

状态：已确认；领域：功能。

仓库注册了 record-import 页面，“我的”中也保留 importBill，但当前模板没有绑定 importBill，全文检索也未找到其他可见跳转入口。导出则只有“入口已预留”的提示函数。

影响：已有的复杂导入能力难以被普通用户发现；功能说明容易与实际可达能力脱节。

建议：将导入放入已有记账工具区域，显示目标账本和只读权限；导出按预留能力说明，不标记为已完成。入口恢复前先验收现有流程。

验收：有写权限的用户可从主界面进入导入；只读访客不获得操作入口且服务端仍拒绝写入。

依据：miniprogram/components/tl-tab-profile/index.js:213

### F05 [P1] 同一主金额位置，在不同模式含义改变

状态：已确认；领域：图表。

周 / 月 / 年主金额是所选方向的总额；自定义 / 累计却使用结余，旁边仍存在支出 / 收入切换。“收支小结”不足以明确告诉用户大数值是结余。

影响：用户连续切换模式时，容易把结余误认为支出或收入。

建议：若保留现有能力，至少明确标注“区间结余 / 累计结余”，并写清方向切换影响的区域；更一致的方案是在所有模式保持主金额为所选方向总额。

验收：五种时间模式任意切换后，主数字有明确指标名、范围和单位；零收入、负结余不产生歧义。

依据：miniprogram/components/tl-tab-analysis/index.wxml:243

### F06 [P2] 近六个月柱图混合完整月与未结束月

状态：已确认；领域：图表。

月度柱图取近 6 个自然月总额；当前月只累计到目前，前几个月则完整。图下虽有截至日期，但柱子本身不区分完整度，均值也把当前不完整月计入。

影响：本月较矮可能只因本月尚未结束；“平均”又未说明是六个月柱均值，与同卡日均口径不同。

建议：当前月使用纹理或明确的“截至 11 日”标注；写“近 6 月月均（含本月未结束）”。比较文案继续保留已实现的同期比较，不把它和柱高比较混为一谈。

验收：11 月 11 日查看时，用户能直接辨认 11 月为部分数据；明确区分日均、月均和上月同期。

依据：cloudfunctions/ourNest/handlers/analysis.handler.js:333；miniprogram/components/tl-tab-analysis/dashboard.js:151

### F07 [P2] 同一柱形点击有三套操作结果

状态：已确认；领域：交互。

周度柱直接进入当日明细；月度柱直接切换当前月份并重新加载；年度柱只选中，再通过“查看该月”进入。图形外观未说明这种差异。

影响：用户无法预测点击会筛选、跳页还是改变整个页面范围。

建议：统一为“点选 → 显示期间、金额和明确的查看入口”，或在各图下明确说明。选中柱应有可见状态，返回时保留原范围。

验收：三种模式点击后都有立即可见、可撤回的反馈；不会无提示改变时间范围。

依据：miniprogram/components/tl-tab-analysis/index.js:475

### F08 [P2] 从分析排行查看记录后，编辑链路中断

状态：已确认；领域：交互。

分析中的单笔记录固定打开 record-detail；该页面没有编辑 / 删除入口。首页和明细则通常根据 readonly 打开 record-edit 或 record-detail。

影响：有编辑权限的用户从分析发现异常记录后，需要回到明细重新找一遍。

建议：统一记录入口策略，或在详情显示服务端 canEdit / canDelete 决定的操作。不能用客户端“非只读”替代成员仅能改自己记录的判断。

验收：Owner、成员本人、成员他人记录、访客四种角色场景分别验收；允许者可完成纠错，无权限者有清楚说明。

依据：miniprogram/components/tl-tab-analysis/index.js:466；miniprogram/components/tl-tab-records/index.js:435

### F09 [P2] 分类图、排行、图标的颜色缺少同一映射

状态：设计判断；领域：图表。

环图按金额排序使用 6 色色板；分类图标按领域分类使用另一套颜色，排名前三又使用独立颜色。分类顺序变化后，同一类别的环图颜色可能改变。环图外标签仅 10px。

影响：颜色难以帮助用户建立长期识别，多个强调色互相争夺注意力，小屏外标签拥挤。

建议：保留线性分类图标；环图与图例采用稳定分类映射，或统一中性色、只强调当前选中项。Top 5 + 其余逻辑已存在，继续保留并让“其余”可展开。

验收：切换相邻周期，同类颜色稳定；320–430px 屏幕上长分类名不互相覆盖；不用单靠颜色区分类别。

依据：miniprogram/components/tl-tab-analysis/chart-options.js:45；miniprogram/components/tl-tab-analysis/index.js:205

### F10 [P2] 部分小字和按钮文字对比度不足

状态：数值验证；领域：界面。

品牌红配白字 3.77:1，绿色配暖白 3.07:1，三级棕灰配页面 3.4:1。现有按钮约 15px / 700、辅助文案约 11–12px（375px 宽时），不能用大字规则为所有文本豁免。

影响：光线强、屏幕小或视觉敏感用户阅读成本更高。

建议：保持品牌主色；为正文 / 按钮文字建立更深的语义色，按文字用途校验。图形与装饰不和正文混用阈值；不要直接全局替换品牌红。

验收：普通文字目标至少 4.5:1；交互状态、禁用态单独审阅。所有建议颜色先在局部方案中验证。

依据：miniprogram/app.wxss:21；miniprogram/components/tl-button/index.wxss:3

### F11 [P2] 首页在无预算状态重复展示收支

状态：已确认；领域：界面。

“本月支出 / 本月收入”双卡之后，无预算时又显示“本月概览”，再次渲染收入、支出，再补结余。首页另有账本类型切换和 Navbar 账本切换。

影响：首屏更多空间用于同一事实，最近记录更晚出现；用户需要判断两组数字是否口径不同。

建议：保留一个主汇总区域：有预算以剩余预算为主，无预算以本月结余或支出为主，收入 / 支出只呈现一次。账本名称与类型共享一个明确切换入口。

验收：预算开启 / 关闭、空账本、收入为零四种状态下，首屏只有一个主视觉锚点；同口径金额不重复出现。

依据：miniprogram/components/tl-tab-home/index.wxml:145

### F12 [P2] 阴影规则与实际实现存在冲突

状态：已确认；领域：组件。

AGENTS 要求除 Tabbar 外无阴影；UI 规范基础原则允许微环境阴影，卡片章节却要求无阴影；全局 .card 当前统一带阴影。静态 UI 检查依然通过。

影响：后续页面维护会沿不同“正确规则”继续扩散，自动检查无法保证视觉一致。

建议：先统一文档与检查基线，再安排视觉变更。依当前协作规则，建议保留 Tabbar 例外，其他容器以背景、细边界和留白表达层级。

验收：同一语义只保留一个规则；.card、分析分类图标及按钮 / 浮层全部复查；不单凭 ui:check 通过宣布设计合格。

依据：miniprogram/app.wxss:228；AGENTS.md:39；docs/UI-GUIDELINES.md:35

### F13 [P2] 预算“消费偏快”没有结合日期进度

状态：已确认；领域：功能。

当前 50% / 70% / 90% 阈值同时决定进度条颜色和“已用过半 / 消费偏快 / 预算预警”文案。月底使用 75% 未必偏快，月初使用 45% 反而可能偏快。

影响：标签表达了超出计算依据的判断。

建议：近期先改成客观用量描述，例如“已使用 75%”；若以后做节奏判断，再明确比较已过天数与预算消耗，不在本轮自行增加新算法。

验收：每条状态文案都能由当前已有数据直接证明；100%以上仍显示真实比例和超支额，进度图形可封顶。

依据：miniprogram/components/tl-tab-home/index.wxml:33

### F14 [P2] 导入核对页信息过载，主操作容易沉底

状态：设计判断；领域：功能。

每行会同时出现来源、商户、分类、疑似重复、交易状态、多个确认按钮等；最多 200 行，确认导入按钮位于长列表之后。技术性临时文件清理状态也进入主要流程。

影响：异常核对和普通确认争夺注意力，用户难以判断剩余工作和最终将写入多少笔。

建议：保留现有校验逻辑；先显示选中笔数 / 合计 / 待确认数量，异常行展开完整信息。确认能力复用 tl-page-actions；底部安全区只归一个组件。清理信息用用户可理解的恢复提示。

验收：正常账单和含重复、退款待审、分类待确认的账单分别验证；可随时看到导入目标和确认总量，重试不会重复写入。

依据：miniprogram/pages/record-import/index.wxml:54

### F15 [P3] 强胶囊、粗字、多彩图标同时出现

状态：设计判断；领域：界面。

公共按钮全部使用胶囊与 700 字重；我的页每个功能都有不同色块；分析排行再叠排名色、分类色和红色金额。它们各自有理由，叠在同一屏上却弱化主次。

影响：视觉负荷来自“处处强调”，而非典型紫色渐变或表情图标。

建议：保持圆角、暖红、Logo 与 Remix Icon；先弱化辅助文字、非关键色块和无意义排名强调。控制胶囊只用于选择状态，不为了 UNSLOP 强行换全局风格。

验收：首屏缩小看时仍可立即指出一个重点；同级组件共享字阶和间距，次操作明确弱于主操作。

依据：miniprogram/components/tl-button/index.wxss:3；miniprogram/components/tl-tab-analysis/chart-options.js:45

### F16 [P3] 维护入口和部分文案超出普通用户任务

状态：已确认；领域：功能。

“清除分类缓存”放在普通设置主列表；版本号固定提示“已是最新版本”，对应方法为空。反馈与更新日志入口被显式隐藏。

影响：普通用户承担缓存维护的心智成本，也可能把静态版本说明当成真实检查结果。

建议：将缓存刷新收敛到现有同步或故障恢复入口；版本只写当前版本，除非确实执行检查。隐藏功能保持标注为不可达能力，不按已上线入口描述。

验收：从用户任务审阅我的页，每项都能回答“我为什么需要点它”；版本状态只表达可验证事实。

依据：miniprogram/components/tl-tab-profile/index.wxml:146；miniprogram/components/tl-tab-profile/index.js:213

| 页面 | 当前能力与入口状态 | 评审重点 |
| --- | --- | --- |
| 登录（login） | 品牌标志、微信快捷登录、登录中状态 | Logo 和单一进入动作可保留；“顺手记一笔”与品牌标题分工清楚即可 |
| 主壳层（index） | 首页 / 明细 / 分析 / 我的 + 中央记账入口 | 懒挂载、Tab 保留状态和分析前后台控制合理；小屏需实测可用高度 |
| 新增 / 编辑记录（record-edit） | 分类网格、快捷金额、算式键盘、账户、日期、备注、家庭归属 | 效率能力完整；新增与编辑结构差异较大，需验证小屏键盘、长分类和保存反馈 |
| 只读详情（record-detail） | 金额、账本、来源、账户、成员、归属、备注标签 | 分析入口进入此页后无编辑出口；长交易号建议折叠并可复制 |
| 筛选结果（record-filtered） | 分析下钻、指定日期 / 类别 / 账户 / 家庭维度、分页 | 这是图表到记录的关键闭环，应固定展示筛选上下文与总量 |
| 分类选择（record-category） | 收支分类树、重选分类 | 与新增记录的分类网格并存；保持同名同图标及选中反馈 |
| 创建账本（ledger-create） | 账本类型、名称、备注、创建确认 | 说明个人 / 共享的区别；无需额外增加装饰性 Hero |
| 账本设置（ledger-settings） | 账本角色、成员概览、编辑 / 删除、创建 / 加入 | 删除按钮用危险语义；长名和成员头像失败需保留稳定布局 |
| 成员管理（member-manage） | 成员与访客、角色、邀请、撤销、退出、所有权转移入口 | 当前代码已含这些入口，旧待办仍称规则未定；本报告不新增或认可未决规则，需单独核对规格 |
| 输入邀请码（ledger-invite-code） | 输入、校验、领取、结果跳转 | 把将加入的账本和权限说清楚；区分无效、已用、过期和网络失败 |
| 加入结果（ledger-join-result） | 领取结果、下一步进入账本 | 结果页保留一个明确主动作；避免成功后用户不知道当前账本是否已切换 |
| 预算设置（budget-settings） | 预算开关、金额、保存 | 只呈现客观使用比例；访客不获得设置能力 |
| 支付账户（payment-account） | 账户列表、新增 / 编辑 / 删除 | 名称是用户识别核心，图标与色块保持辅助；历史记录引用边界需说明 |
| 快捷金额（quick-amount-settings） | 高频金额配置、保存 | 与数字键盘直接对应；金额格式、顺序和保存结果保持一致 |
| 分类管理（category-manage） | 收入 / 支出及分类层级入口 | 层级导航使用相同词汇，分类删除与记录迁移后果可见 |
| 分类操作（category-operation） | 列表、新增 / 编辑 / 删除、图标选择 | 每行独立 card 可收敛为连续列表；长列表操作与底部按钮避免争抢 |
| 分类图标（category-icon-picker） | 本地 Remix Icon、检索和选择 | 保留线性图标；检索、已选项和回到表单的状态需一致 |
| 账单导入（record-import） | 文件预览、分类确认、重复识别、中断恢复、结果 | 完整页面存在但入口缺失；优先解决可达性和批量核对负担 |
| 资料编辑（profile-edit） | 头像、昵称、保存 | 微信头像与系统头像回退一致；上传失败要保留输入 |
| 意见反馈（feedback） | 反馈表单与提交 | 页面注册存在；我的入口隐藏，不能算普通用户当前可达的主要功能 |
| 反馈历史（feedback-history） | 反馈记录、详情状态 | 页面存在；随反馈入口一起检查可达链路，不默认等同已开放功能 |

## 组件与打磨顺序

- **壳层与导航**：tl-navbar、tl-container、tl-tabbar。账本上下文、返回、主导航、底部安全区；现有边界值得保留。中央 + 应补充可读“记一笔”语义，访客状态可直接说明。
- **状态与反馈**：tl-skeleton、tl-empty-state、tl-feedback-host。优先修复二次加载空白；无账本、无记录、方向无数据、加载失败各自需要准确下一步。
- **操作与浮层**：tl-button、tl-page-actions、tl-bottom-sheet、tl-dialog。保持唯一主操作；通用 Dialog 默认允许遮罩关闭，执行删除或不可中断写入时逐处验证。普通确认和危险确认需要可区分。
- **记账与领域**：tl-record-form、tl-category-tree、tl-ledger-switcher、tl-budget-progress。算式键盘和快捷金额是产品强项；公共与多人归属不自行改规则；预算条封顶但文字保留超支比例。
- **图表与记录**：tl-analysis-record、tl-tab-analysis。统一图、表、金额、分类与明细口径。ec-canvas 是第三方适配层，生命周期控制已存在，不能把计划中的旧故障当作已复现现状。
- **图标与 Tab 内容**：tl-icon、tl-tab-home、tl-tab-records、tl-tab-profile。继续使用本地 Remix Icon；保留不同业务布局，统一间距、字阶和色彩语义。

按 UNSLOP 的九个层面推进：间距 → 色彩 → 图标 → 文案 → 字体层级 → 布局 → 细节 → 视觉 → 动效。保持品牌、浅暖背景、现有圆角和本地 Remix Icon；先去重复和弱化辅助强调，图表成为分析页主要内容。

普通文字以至少 4.5:1 为设计评审目标。本次计算：品牌红 / 白字 3.77:1；绿色金额 / 暖白 3.07:1；三级文字 / 页面 3.4:1；正文 / 页面 13.99:1；次级文字 / 页面 5.54:1。不能据此宣称整屏无障碍合规。

## 优先级与验收

第一批：F01–F05，修正图表取数、加载反馈、比例、导入入口和指标命名。
第二批：统一点击、部分周期说明、记录纠错、图表颜色、预算文案与导入核对。
第三批：首页去重复、阴影规则收敛、局部文字可读性和组件语义打磨。

验收需覆盖：纯收入 / 纯支出 / 无记录 / 负结余，历史完整期 / 当前部分期 / 跨年 / 长期累计，Owner / 成员本人 / 成员他人记录 / 只读访客，首次加载 / 二次刷新 / 断网 / 快速切换 / 前后台，320–430px 屏幕和大字号。金额应按分守恒。

成员退出、所有权转移、邀请生命周期的入口已见于当前代码，但规则与待办仍称待决。需单独核对规格，不由本次 UI 报告自行定义。
