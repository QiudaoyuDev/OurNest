# 个人与家庭记账开发计划

> 状态：进行中。本文根据 bill-dev 对比分析形成，是后续开发的执行路线；已完成任务的实际交付与验证结果记录在对应任务中，待决策规则不因本计划自动生效。
> 范围：以微信小程序为主，优先个人记账、消费统计、账单导入，再完善家庭对比与汇总。

## 1. 产品目标

让个人和家庭能够快速记录消费，并准确回答：钱花在哪里、近期是否多花、历年如何变化、家庭各成员与公共消费分别是多少。

核心需求：

- 记录消费类型、金额、日期及必要备注，支持收入与支出。
- 重点关注餐饮、交通、购物，其他分类保持可管理。
- 查看单月、多月、单年、多年的汇总、趋势和对比。
- 导入历史账单，能够核对结果、识别疑似重复，并安全重试。
- 支持家庭成员互相对比和家庭汇总，明确录入、付款、消费归属的区别。

实施原则：复用现有能力，不重复建设；先统一口径，再扩展图表；统计必须能追溯到明细；不能为了家庭功能增加普通个人记账的必填负担。

## 5. 阶段一：记得快、看得准

目标：在现有模型内改善个人记账、统计可解释性及导入可靠性，不引入未经确认的家庭分摊规则。

### A1. 优化日常与连续记账（已完成）

工作内容：

- 先核验现有记账流程；已有等价能力则补齐体验与测试，不重复增加入口。
- 支持“保存并离开”与“保存后再记一笔”。连续记账成功后保留日期、分类等可复用条件，清空金额和本笔独有内容；具体保留项在实现设计时逐项明确。
- 失败时保留输入；保存进行中禁止重复触发，不显示未经云端确认的成功。
- 在现有分类选择中优化常用餐饮、交通、购物操作；常用内容建议不是必填项。

验收：连续记录至少三笔不需反复选择相同日期和分类；保存失败不丢输入；连续点击不产生多笔意外记录；个人与共享账本权限行为不变。

交付记录：新建记录页已提供“保存并离开”与“保存后再记一笔”。后者在云端确认后保留类型、分类、日期和账户，清空金额、备注和标签并留在表单；编辑记录仍为单一保存操作。失败保留输入，提交中拦截重复请求。已通过 `npm run test`（59 项）、`npm run cloud:check` 与 `npm run ui:check`；`npm run verify` 因当前工作区缺少 `prettier` 命令未完成。

### A2. 明确分类与交通车费范围（已完成）

现有交通子分类：公交地铁、打车、加油充电、停车。保留“交通”一级分类，不重复创建含义重叠的“车费”一级分类。

工作内容：

- 确认车费主要指乘车费用、养车费用，还是两者都需要。
- 候选补充项：火车高铁、过路过桥、维修保养、车险、其他车费；仅按确认结果加入。
- 分类改动分别设计新账本初始化、已有账本处理；不得假设修改默认数组即可更新全部旧账本。
- 不自动迁移或重分类历史记录；确需迁移时另行设计可恢复、可重试方案。

验收：无重叠一级分类；旧分类和历史金额不丢失；初始化或补齐重试不重复建类；改名、隐藏或迁移后的统计与历史展示符合确认规则。

交付记录：确认保留“交通”一级分类，新增火车高铁、过路过桥、维修保养、车险和其他车费。新账本初始化包含这些系统分类；已有账本在分类读取时只补齐缺失项，同名自定义分类不覆盖，且修复后递增同步版本。未迁移历史记录。已通过 `npm run test`（61 项）、`npm run cloud:check` 和 `npm run ui:check`。

### A3. 统一时间与金额比较口径

工作内容：

- 梳理现有月、年、自定义等模式的范围、趋势粒度和上期算法，形成测试与接口口径说明。
- 延续当前月对上月同期、当前年对去年同期，完整历史周期对完整上期的语义；页面明确展示比较范围。
- 月度同比作为后续扩展，与月度环比明确区分，不混用名称。
- 统一金额汇总与展示精度；比较基数为零时不显示无穷大或误导性百分比。
- 收支流量中的真实零值时间桶补零；未来期间、缺失数据与零消费不得混淆。

验收：覆盖月末、大小月、闰年、跨年、零基数、仅收入、仅支出及空账本；同一范围首页、分析和明细总额能按各自明确口径对账。

### A4. 建立统计到明细的下钻链路

依赖：A3。

工作内容：

- 分类排行或占比可打开对应日期范围和分类的明细。
- 趋势中的月份可打开该月明细；预算下钻只使用有效的预算周期，不伪造历史预算。
- 查询条件经服务层传到云端，统计和明细共用同一筛选定义；不得只筛选已加载页。
- 明细分页仍遵守 `{ date, id }` 游标契约；筛选变更必须覆盖全部调用方和相关索引评估。

验收：分类金额等于该筛选范围全部明细合计；跨月、自定义范围、同名子分类、切换账本和返回分析页时条件准确；只读访客只能查看。

### A5. 建设可校对、可重试的模板导入

建议分三个独立交付单元：预览校验、幂等提交、结果与重试。

工作内容：

- 将现有直接写入流程调整为“解析预览 → 人工核对或排除异常行 → 确认写入 → 结果核对”。
- 预览展示日期、收支、金额、分类、账户、备注及错误原因；服务端提交时重新校验权限和数据，不信任预览结果。
- 区分“确定重复”与“疑似重复”：可信来源交易标识可作为去重依据；相同日期、金额和商户仅用于提醒，不直接删除正常消费。
- 在并发、超时、重复确认、重开页面重试等情况下保证同一导入请求不重复写入。设计导入批次、行结果和幂等边界，不能只依赖按钮禁用或文件名。
- 部分成功时能够识别已成功行并仅重试失败行，避免整批重导。
- 明确文件大小、行数和执行时限；现有 200 行上限在验证前不擅自提高。
- 规定临时文件及导入中间数据的访问权限、保留周期和清理方式，不把真实账单提交仓库。

验收：预览未确认不写入；无效自然日、非法金额和异常分类有明确提示；重复消费可经确认保留；重复提交及部分失败重试无重复写入；非法访问其他用户文件或批次被服务端拒绝。

阶段出口：A1–A5 均有可运行闭环和测试；个人记账与现有共享权限无回退。阶段二的统计任务只依赖相应统计基础，不必被独立的导入任务长期阻塞，但阶段一整体完成前不能标记阶段完成。

## 6. 阶段二：多期对比与真实账单导入

目标：补齐多月、多年和重点分类对比，家庭先提供现有数据能准确表达的“成员录入”维度。

### B1. 常用多月、多年趋势

依赖：A3。

- 提供近 6/12 个月、近 3/5 年等快捷范围，复用现有趋势计算。
- 支持收入、支出、结余，并按范围明确日、月、年粒度。
- 区分趋势范围与比较范围：现有年度近五年趋势固定围绕当前年，查看历史年度或自定义区间时是否随所选期间移动，必须明确设计并同步契约。
- 新增范围上限、返回桶数和性能基线，避免无限全量读取。

验收：横轴有序、真实零值完整、当前未结束周期标识清楚；长期趋势合计可与对应明细核对；切换范围无旧请求覆盖。

### B2. 自选多期与重点分类对比

依赖：A3、A4、B1。

- 用户可选择两个或多个自然月，或两个或多个自然年进行并排对比。
- 对比选择数量、时间跨度、非完整周期处理及默认基准，先在交互设计中明确并设置合理上限。
- 至少覆盖总收入、总支出、结余；支持餐饮、交通、购物等分类专项比较。
- 分类汇总按稳定分类身份与层级处理，不能只凭名称合并；导入的未关联分类需要明确映射策略。
- 同比、环比与自选比较使用明确标签；不同长度自定义区间不默认声称可直接同比。

验收：两个及多个非连续月份、跨年月份、多年和分类切换均正确；金额差值、比例与所选基准一致；每个可下钻数据点与明细一致；分类改名不造成错误合并或丢失。

### B3. 成员录入维度的家庭对比

依赖：A3、A4；领取前确认成员数据可见范围。

- 在共享账本中比较各成员录入的支出、笔数及重点分类；只展示现有数据可以证明的维度。
- 明确使用“成员录入支出”等文案，不称为实际付款额、个人消费额或承担额。
- 提供同一范围的家庭账本总额；一条记录只计一次。
- 成员条件下钻由服务端授权，不能凭客户端提交成员标识跨账本查询。
- 当前预算是账本级配置，不自动按成员拆分。

验收：成员录入合计与账本合计在相同成员覆盖范围下可解释、可核对；成员失效或退出后的处理只能按已确认规则实现；访客与成员的查询权限均有测试。

### B4. 适配真实来源账单

依赖：A5；根据用户实际账单来源排序。

- 先取得脱敏或人工合成的微信、支付宝等样例，逐种确认字段、表头和编码，再逐个适配，不宣称支持所有银行。
- 明确交易成功/关闭、退款、转账、信用卡还款、提现、充值等记录是否属于消费，避免重复计入收支。
- 使用来源与来源交易标识辅助去重；不同来源可能是同一笔交易，跨来源匹配先作为疑似重复处理。
- 分类映射必须可核对；无法确定的条目进入待确认，不静默猜测。
- 展示每条记录的来源及导入结果，支持追踪批次；涉及新增数据字段时同步数据文档与测试。

验收：每个来源独立通过固定样例；金额、日期、状态和退款处理符合确认口径；同源重导与跨源疑似重复有明确结果；部分失败可安全重试。

阶段出口：多月、多年与重点分类比较可用；家庭成员录入统计不误导；已声明支持的账单来源均完成端到端验证。

## 7. 阶段三：真正的家庭消费与归属统计

目标：在明确产品规则后，区分录入、支付和消费归属，提供个人与家庭公共消费分析。

### C1. 确认家庭模型与数据可见范围

这是开发阻塞任务，不允许直接用 bill-dev 的规则替代用户决策。

必须确认：

- 家庭对比优先比较谁付款、消费归谁，还是两者都需要。
- 家庭汇总仅覆盖一个共享账本，还是汇总多个个人账本；后者必须另行设计授权、隐私与跨账本去重，不能因家庭成员关系自动公开私人账本。
- 是否允许代记、代付；录入人与付款人可否不同，以及谁能编辑该记录。
- 是否需要无登录账号的家庭成员，以及如何与微信用户关联。
- 公共消费单独展示还是分配到个人；若分配，按什么规则、如何处理分币余数。
- 是否需要一笔消费归属多人；选择具体多人和选择家庭公共是否具有不同的历史含义。
- 成员加入、退出、移除与改名后，历史记录和统计怎样保持稳定。
- 家庭成员及访客能看到哪些记录和个人统计。
- 历史账单中无法确认的付款人与归属如何展示；不允许默认认为录入人就是付款人。

交付：用户确认的规则、数据模型、权限矩阵、统计样例和历史数据方案；更新所属规格后才进入 C2。

### C2. 实现付款与消费归属

依赖：C1。

- 服务端维护记录创建者身份；付款人与消费归属按确认后的模型校验，不接受客户端伪造身份或权限。
- 更新新建、编辑、详情、筛选、导入、统计及全部相关调用方，避免只改记账表单。
- 个人记账沿用简洁默认体验，不要求用户每笔重复填写家庭字段。
- 无法确认的历史数据明确标注未知或按已批准规则处理，不静默推断。
- 若需要迁移，采用可恢复分批流程；明确读写切换、备份、回滚和完成确认。版本策略需正式评审，不擅自更改当前 `schemaVersion: 1` 契约。

验收：覆盖本人消费、代付、代记、公共消费及确认支持的多人场景；历史记录无误归属；编辑权限仍由服务器判断；导入与手工记录遵循同一契约。

### C3. 家庭汇总与个人消费对比

依赖：C2，并复用 B1、B2 的时间比较基础。

- 根据已确认范围提供家庭总额、各成员付款、个人消费与公共消费。
- 支持按成员、时间、餐饮/交通/购物等分类分析和下钻。
- 家庭总额不重复计数；若公共消费不分配到人，则明确展示“个人消费合计 + 公共消费 = 家庭消费”，不把付款额和消费额相加。
- 如经确认引入多人分配，金额使用可靠精度计算，分配总和必须等于原始金额，历史成员变化不得偷偷改变旧记录口径。

验收：准备可手工计算的双人及多人家庭样例，对账到分；付款视角、消费视角和录入视角的差异可解释；任何无权用户不能从汇总或下钻获取私有数据。

阶段出口：家庭规则已确认、历史数据有明确解释、权限和统计均可验证；未获确认的分摊或结算不纳入完成范围。

## 8. 依赖与建议交付顺序

建议默认顺序：

1. A1 → A2 → A3 → A4 → A5。
2. B1 → B2 → B3 → B4。
3. C1 → C2 → C3。

依赖说明：

- A2 的分类补充被决策阻塞时，可先执行 A3，不自行决定“车费”范围。
- B1/B2 依赖统计基础，B4 依赖导入基础，可在对应基础稳定后独立交付。
- B3 不依赖新增付款/归属字段，但必须保持“录入”语义与既有权限边界。
- C1 的产品讨论可提前进行，C2/C3 必须等待规则确认。
- 每项优先做“云端契约与测试 → 服务层 → 页面闭环 → 回归”，不把仅完成一层视为功能完成。

暂不承诺工期。每项领取时根据复核后的工作量拆分为可独立验收的小任务；新增依赖、数据迁移或跨账本需求需重新评估范围。

## 9. 统一工程、安全与验证要求

### 工程与权限

- 保持 `{ route, payload }` 和 `{ ok, data }` / `{ ok, error }` 协议，前端业务请求统一经过 `miniprogram/services/`。
- 服务端重新读取用户和账本判权；只读访客不得写入、导入或导出。
- 共享账本成员只可编辑/删除自己的记录，Owner 可管理全部；C1 若提出不同规则，必须先正式确认并更新权限契约。
- 新建记录、分类调整与导入等成功后遵循账本同步版本和缓存失效约定，不能只更新当前页面而让其他成员看到旧汇总。
- 长时间导入、分类迁移及数据修复使用分批、可恢复流程，不用单个大请求假设永远成功。
- 先在 test 环境演练；涉及迁移、删除、权限或生产数据时必须准备备份与回滚，不在本计划执行期间直接修改生产数据。

### 统计与导入测试矩阵

至少覆盖：

- 空账本、仅收入、仅支出、零基数、重复金额、同日多笔和小数金额。
- 月末、大小月、闰年、跨年、完整历史周期与进行中的同期比较。
- 两个及多个对比周期、分类改名、同名不同父分类、未关联分类和记录分页。
- 两账号共享、只读访客、无权用户、权限变化、成员显示变化及相关已确认历史规则。
- 文件格式错误、无效自然日、缺字段、行数超限、预览取消、重复点击、超时、部分成功、并发重试和跨来源疑似重复。
- 快速切换账本/时间/成员、弱网、旧请求晚返回，以及写入后各统计视图刷新。

### 每项交付检查

- 运行受影响测试；代码变更通常执行 `npm run verify`。
- UI 修改执行 `npm run ui:check`，关键视觉变更执行 `npm run visual:check`。
- 按 `docs/REGRESSION.md` 在微信开发者工具及真机完成相应手工回归；家庭功能至少使用两个测试账号。
- 对统计、导入任务记录同规模样例下的耗时和正确性基线；不以新增客户端永久统计缓存掩盖查询问题。
- 同步更新行为、数据、权限和回归文档；检查结果如实记录，未运行不得写为通过。

## 10. 暂不纳入本轮的功能

- 自动家庭 AA、按收入比例分摊、应收应付及转账结算建议。
- 家庭资产、负债盘点、养老预测及投资收益模型。
- 独立 PC/H5 客户端与账号密码体系。
- AI 文本、语音或图片记账；待手工录入与文件导入稳定后单独评估。
- 未授权的跨个人账本汇总、自动公开家庭成员私人账单。
- 邀请生命周期、Owner 转移等既有未决规则，除非用户另行明确，不随本计划顺带实现。

## 11. 后续开发的领取模板

每次开始任务时填写：

- 任务编号与目标：例如 A3，统一时间与金额比较口径。
- 基线复核：哪些已有、哪些缺失，是否与本文记录不同。
- 前置条件：依赖是否完成，是否存在待产品确认项。
- 本次范围：涉及的云函数、服务层、页面、数据与规格。
- 验收样例：输入、统计范围、预期金额和权限结果。
- 验证与发布：实际命令、手工回归、迁移及回滚要求。

完成后记录：交付内容、真实验证结果、未完成范围，并更新唯一待办入口。本文作为开发路线持续维护，不用完成标记代替测试证据。
