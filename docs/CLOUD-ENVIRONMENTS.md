# 云开发环境切换

环境配置的唯一入口是 `miniprogram/config/cloud-env.js`。

- 开发版（`develop`）和体验版（`trial`）自动使用 `test`。
- 正式版（`release`）自动使用 `production`。
- `production.id` 当前留空；创建生产环境后只填写该配置项。
- 本地临时切换可设置 `LOCAL_OVERRIDE` 为 `test` 或 `production`，提交前必须恢复为空。
- 环境改变时，小程序会清除本地登录、账本和分类缓存；旧记录副本在启动时清理，避免测试与生产数据混用。
- 正式版缺少环境 ID 时必须明确失败，不能回退或误连测试环境。

上传正式版本前：

1. 确认 `production.id` 已配置。
2. 在生产环境部署同名 `ourNest` 云函数。
3. 核对生产环境集合、索引和安全规则。
4. 确认测试数据、用户数据和密钥未写入仓库。
5. 运行 `npm run verify` 并完成 `docs/REGRESSION.md`。

## 云函数名称迁移与回滚

业务云函数的新部署名称为 `ourNest`，本地目录和客户端调用名必须一致。重命名目录不会重命名云端已有的 `tomatoLedger`，上传后需按新函数核验配置。

- 先备份原函数代码、依赖及云端配置，并盘点定时/HTTP 触发器、外部调用、权限、告警和日志查询；仓库不能证明控制台不存在这些依赖。
- 先在 test 部署 `ourNest`，核对运行时、内存、超时（仓库配置为 20 秒）、环境变量和权限，并使用两个测试账号完成登录、账本、记录 CRUD、分页、导入、邀请、分类迁移和预算回归。测试数据不得导入生产环境。
- 验证通过后，在 production 部署 `ourNest` 并完成同环境核验，再发布调用新名称的小程序。未创建的生产环境不需要为本次本地修改提前创建。
- 若已有旧客户端，云端保留 `tomatoLedger` 供旧版本使用；源码只维护新名称，不增加自动重试旧函数的逻辑，避免写请求重放。兼容期内的安全修复需同步部署到两个函数，数据库与协议必须保持兼容。
- 结合旧版本使用情况及旧函数调用日志确认不再有请求，并留存备份后，才能删除旧函数；不能仅按固定天数删除。
- 新函数异常时优先恢复 `ourNest` 的已验证代码及配置；若需回退小程序，应先确认 `tomatoLedger` 仍可服务旧版本。函数改名不迁移数据库，不能通过恢复旧数据库快照回滚名称，以免覆盖期间的新写入。

结构化请求日志的新 `type` 为 `ourNest`，`errorLogs.type` 为 `ourNestError`；历史 `tomatoLedger` / `tomatoLedgerError` 不改写，兼容期排错需同时检索新旧类型。此次名称迁移保留本地缓存键、数据库集合、云文件 ID、品牌资源和导入模板路径，不要求用户重新登录。
