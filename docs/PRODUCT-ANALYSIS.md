# OurNest 个人与共享记账小程序综合分析报告

## 0. 阅读说明与结论摘要

### 分析依据与边界

本报告基于当前仓库源码、规格、数据契约、待办及测试设计，结合本轮检索到的同类产品官方资料。分析基线为提交 `d4c223e0682340a2ab6338fc9f67678c91fe99ce`，开始检查时工作区干净。

- 已进行：前端业务、云端权限与写入、工程质量三个方向的只读分析；重点并发与撤权结论另经独立只读复核。
- 未进行：本轮单元测试、`npm run verify`、开发者工具交互、真机体验、CloudBase 实际请求、安全规则部署检查、备份恢复演练及真实用户访谈。
- “已实现”表示存在实际实现及调用链，不表示已经通过本轮运行验证或生产验收。
- “建议”不等于已确认需求；成员退出、Owner 转移、AA 分摊等规则仍需产品决策，不能按本报告直接实现。
- 竞品信息来自官方站点检索结果；部分网页直接抓取因 DNS 解析失败未成功。因此仅比较能由官方材料支持的能力，不比较实时价格、付费限制、下载量或精确热度排名，也不声称实际试用了这些产品。

### 一句话结论

**OurNest 已经不是简单的记账演示，而是具有较完整业务基础的轻量个人与共享收支工具；当前最需要补的不是更多图表，而是“数据可信、关系可管理、数据可带走、异常可恢复”的长期使用闭环。**

建议定位为：

> 在微信里，帮助个人和亲密小群体低负担记清收支，并看懂钱由谁支付、用于谁或什么共同事项。

不宜现阶段同时承诺“完整资产管理”“全自动记账”“实时协作”“AA 自动结算”或“完整离线记账”。

### 核心判断

1. **个人记账：基础可用，长期使用能力不足。** 录入、明细、分类、分析、预算已成链，但导出尚为占位，退款、转账、周期账单、资产对账缺少独立业务模型。
2. **共享记账：有差异化基础，协作生命周期尚未闭合。** 区分录入人、付款人、消费归属是亮点；退出、转移、角色调整、操作追溯与同步预期仍不完整。
3. **工程设计：已经重视一致性，但不能把设计意图视作完整保证。** 有事务、版本围栏、分页、导入幂等、分类迁移恢复；同时仍存在撤权和并发写入窗口。
4. **产品方向：应先做可信的小工具，再做复杂财务工具。** 优先保护钱和关系，不优先追逐 AI、OCR、皮肤或更多统计维度。
5. **运营成熟度：当前证据不足以宣称正式运营就绪。** 这不等于已经证明线上不可用，而是缺少真实云端、设备、备份和性能证据。

## 1. 当前实际业务逻辑

### 1.1 身份与账本

用户以微信身份登录，维护个人资料和当前账本。用户可创建个人或共享账本，并在有权访问的账本间切换。前端通过服务层调用 `ourNest` 云函数，使用 `{ route, payload }` 协议。

服务端角色主要为：

- Owner：管理账本、邀请、成员及全部记录。
- 成员：在共享账本写入，只能编辑或删除自己录入的记录。
- 访客：只读；个人账本也可分享给只读访客。

重要边界：**账本类型决定协作方式，访问角色决定能做什么，两者并不是同一个概念。** “个人账本”并不必然意味着只有本人看得见。

主要依据：`goal-and-requirements.md`、`architecture.md`、`cloudfunctions/ourNest/shared/helpers.js:301`、`cloudfunctions/ourNest/handlers/ledger.handler.js:282`。

### 1.2 日常记账

当前主链路是：

选择账本 → 选择收入/支出与分类 → 输入金额、日期、账户及备注等 → 共享场景确认付款和消费归属 → 云端校验权限与字段 → 写入记录并更新版本 → 通知首页、明细、分析刷新。

已经有表达式金额、快捷金额、快捷备注、标签、连续记账、失败保留输入、保存防重复、编辑冲突提示与删除确认。记录写入需要联网确认，没有离线写入队列。

**账户目前是支付渠道名称，不是资产账户。** 它可用于筛选和统计，但不能据此计算真实银行卡余额、信用卡负债或净资产。

主要依据：`miniprogram/pages/record-edit/index.js:616,650,672`、`miniprogram/services/record.service.js:6`、`miniprogram/pages/payment-account/index.js:35`。

### 1.3 明细、统计与预算

- 首页包含当月收支、预算进度和最近记录。
- 明细按账本、时间和收支类型浏览，使用游标分页；分类、账户、共享成员维度可下钻。
- 分析已有周期切换、趋势、分类、账户以及付款/消费/录入视角，不只是静态图表。
- 金额分析逐笔转成“分”累计；响应还校验上下文、有限金额与金额守恒，避免缺字段时假装为零。
- 预算是账本级月总预算，主要展示当前月执行，不是分类预算、历史预算版本或完整预算规划系统。

注意：数据库文档描述了多期自选比较，但当前前端服务未接入独立的 `ledger/analysis/compare` 调用。不能把后台接口或文档描述计为完整面向用户的功能。

主要依据：`miniprogram/components/tl-tab-home/index.js:193`、`miniprogram/components/tl-tab-records/index.js:194`、`miniprogram/components/tl-tab-analysis/index.js:727`、`miniprogram/services/ledger.service.js:13`、`docs/DATABASE.md`。

### 1.4 导入

当前已实现模板、微信支付与支付宝账单文件的识别、预览、选行、分类确认、异常交易人工确认、分批写入、同源交易去重、中断续传及临时文件清理重试。

这不是一个只有上传按钮的功能，服务端也有凭证绑定、文件哈希、批次进度及每次十行的事务提交。

但现有限制和成本比较明显：

- 最多 5 MB、200 行，不适合直接迁入多年历史。
- 来源分类不自动映射到现有分类，仍需用户确认。
- 退款、转账、还款、充值、提现等需要人工判断收支方向。
- 超过一定记录范围后，跨来源疑似重复比对不完整，会提示人工检查。
- 已开始的批次不能简单取消，未完成批次会限制选择新文件。

**结论：导入的安全设计较认真，但“导得进”和“轻松迁入”之间仍有距离。**

主要依据：`miniprogram/pages/record-import/index.wxml:23,48,54`、`cloudfunctions/ourNest/handlers/record.handler.js:676,1047,1181`、`docs/DATABASE.md`。

### 1.5 共享协作与邀请

当前已实现 24 小时单次绑定邀请码、Owner 邀请成员/访客、邀请码预览、领取事务、尝试限流、重复领取状态及成员移除。

仍需区分：

- 已有成员领取新邀请码不会自动升级角色；访客拿到成员邀请也不会自动变为成员。
- 已登录用户打开分享链接后，结果页会直接尝试加入，没有独立的加入前确认步骤。
- 未发现主动退出、Owner 转移、邀请撤销或完整角色调整的业务闭环。
- 共享同步以版本校验和重新读取为主，前台约两分钟校验，不是推送式实时协作。

主要依据：`cloudfunctions/ourNest/handlers/ledger.handler.js:282–435`、`miniprogram/pages/ledger-join-result/index.js:41,82`、`docs/CACHE-POLICY.md`。

### 1.6 明确未形成的能力

以下不是“已有但待优化”，而是目前未形成完整用户闭环：

- 账单导出：`miniprogram/components/tl-tab-profile/index.js:201` 仅提示入口预留。
- 更新日志：同文件 `:209` 为占位。
- 资产余额、账户转账、负债、对账、净资产。
- 退款关联、报销状态和周期账单等独立账务模型。
- AA 比例/金额分摊、成员应收应付和结清。
- 完整离线写入与冲突恢复。
- 生产备份、迁移及恢复演练。

不要求把这些全部补齐。关键是明确哪些属于产品定位，哪些应诚实保留为边界。

## 2. 当前项目做得好的地方

### 2.1 共享模型优于简单“按录入人排行”

录入人、付款人、消费归属分开，能表达代记和代付。许多简单共享工具把“谁记的”当作“谁花的”，容易误导；OurNest 已在数据模型上避免这一点。

历史数据和导入数据不强行推断付款或消费成员，而是保留未知，也比制造虚假的精确统计更可靠。

### 2.2 核心数据闭环比界面完成度更扎实

写入后有统一失效通知、版本刷新；明细不是把当前一页当作全部统计；分类、账户和成员分析可回到记录验证。这些设计直接影响用户是否信任数字。

### 2.3 已考虑真实异常，而不只考虑成功路径

导入有幂等和续传，分类迁移有阶段进度，编辑有版本冲突，保存失败保留输入。相对于大量 CRUD 式记账项目，这是有价值的工程积累。

### 2.4 小程序与共享场景契合

无需安装独立 App，微信身份与邀请路径减少了邀人门槛，适合情侣、家人、同住者或小型活动。这个优势来自场景匹配，而不是功能数量。

代价是依赖微信入口、平台能力和网络条件；不能直接照搬原生 App 的后台自动化或本地数据库体验。

### 2.5 有持续维护的基础

服务层、云端权限、公共组件、语义 Token、质量脚本和回归清单已建立。现阶段没有必要为“专业感”重写成微服务或换前端框架。

视觉规范已有温暖、统一的方向。由于本轮没有真机观察，只能肯定规范与复用基础，不能据此宣称界面已经流畅、易用或无布局问题。

## 3. 从用户角度看，哪些地方最容易失去信任

### 3.1 “我记了几年，能不能拿走数据？”

能导入但不能导出，会形成单向迁入。即便云端没有丢数据，用户也会担心停服、换软件或误删除后无法处理。

建议把导出视为基础信任能力，而不是最后补的便利功能。导出和备份应分别设计：

- 导出服务于用户查看和迁移，保留日期、金额、分类、来源及共享归属等有意义信息。
- 备份服务于灾难恢复，要能恢复记录关系、分类和权限等对象。
- 用户能拿到 CSV 不代表服务端已具备恢复能力；云端定期备份也不能代替用户导出。
- 继续保留访客不可导出的现有边界，其他角色的导出范围及敏感成员标识脱敏需明确。

### 3.2 “我们不再一起记账了，怎么办？”

共享记账不只是一起加入，还包括关系变化。没有退出、转移与历史归属规则，用户会在最敏感的时刻无路可走。

需要先决定：退出后能否看历史、是否能再编辑自己的旧记录、付款/消费归属如何显示、Owner 不再使用时怎么办，以及移除与自主退出是否同义。

本报告不替用户决定这些政策。建议先保证历史金额不被退出动作静默改写，再讨论访问权与展示策略。

### 3.3 “为什么算我花的？为什么我不能改？”

现有权限跟随录入人，而消费分析可能按付款人或消费人。A 替 B 录入一笔由 B 支付、B 消费的记录时，B 虽然被统计为相关成员，却不能编辑这笔由 A 录入的记录。

这不是必然错误，但必须明确：**归属不是操作权限。** 建议优先解释规则并支持纠错协商，而不是直接让所有人任意修改他人记录。

### 3.4 “我只是看了邀请，怎么已经加入？”

分享链接进入后自动领取，降低步骤但减少了知情确认。共享记录涉及消费隐私，建议先明确账本、邀请者、角色及可见范围，再由用户确认加入；保留令牌单次绑定与重复请求幂等不变量。

这是流程建议，不代表当前行为已经违反平台规则。

### 3.5 “对方记完了，我怎么没看到？”

两分钟轮询和手动同步对于轻量共享可以接受，但与“实时同步”的宣传预期不同。应明确刷新机制，避免用户误以为保存失败而重复补记。

也要区分“服务端已撤权”和“本机曾缓存的历史数据”。前者必须立即落实在接口授权中，后者需要缓存清理策略，不能承诺远程收回用户已经看到或保存的内容。

## 4. 最重要的业务语义缺口

### 4.1 收支不等于资金流动

目前记录类型只有收入和支出。对于纯消费台账可以成立，但遇到转账、退款和还款时容易出现统计歧义。

例一：银行卡转入微信 500 元，再用微信买菜 100 元。若把转入算收入、转出算支出，会虚增收支；真实消费只有 100 元。

例二：消费 300 元后退款 100 元。若退款作为收入，得到支出 300、收入 100、净流出 200；这在现金流口径下可解释，但“本月消费”和分类预算是否应算 200，当前没有完整退款关联语义。

建议：先确认产品采用现金流、净消费还是两者并列，再决定退款关联与排除转账的方式。不要为了覆盖场景直接允许负金额，也不要把退款统一塞进普通收入后宣称消费分析已经准确。

### 4.2 共享分析不等于 AA 分摊

当前 `public` 和 `multiple` 消费按录入人展示，保证一笔只算一次，但不记录每人应承担的份额。

例如 A 录入并支付一顿 300 元的三人聚餐，标为“多人”：

- 能表达 A 付款，以及这是多人消费。
- 消费视角按录入人归集，不代表 A 实际独自消费 300 元。
- 不能推导 B、C 各欠 A 100 元，因为没有参与者、分摊比例和结算模型。

所以当前适合“共同了解花费”，不适合直接宣称“公平分账”。若以后要服务旅行或合租结算，应单独定义参与者、精确分摊、分币余数、垫付、退款和结清，不能从现有图表反推出债权。

### 4.3 账户名称不等于资产实体

现有账户以字符串名称保存，删除账户保留历史名称，能避免历史记录被抹掉；但不能支撑账户余额、归属、改名追踪、停用和跨账户转账。

如果坚持轻量消费台账，建议继续明确“支付渠道”的边界。如果要做资产管理，再建立稳定账户 ID、期初余额、调整记录和转账关系，不能仅在现有名称列表旁加一个余额字段。

### 4.4 预算目前是观察工具，不是决策工具

月总预算能回答“还剩多少钱”，难以回答“哪类该控制”“本月剩余每天还能花多少”“下月是否延续”。

建议优先补预算口径说明和历史预算快照，再考虑分类预算、固定支出与日均可用金额。预算应帮助规划，不宜默认阻止必要支出或制造重复提醒。

### 4.5 个人与共享账本之间还缺使用策略

一笔支出只能放共享账本还是也要在个人账本记录？用户在两处记录会不会误以为是两笔不同消费？当前未形成跨账本汇总或关联去重能力。

建议先明确“统计只覆盖当前账本”，并提供可理解的使用约定。不应未经隐私决策就将所有个人记录汇入共享分析。

## 5. 工程师视角：应优先处理的具体风险

以下是源码级发现，不是本轮线上事故复现。前五项已由独立只读审查复核；严重性随触发条件与真实环境而变，不把所有项目一概列为上线阻断。

### 5.1 高优先：被移除成员登录仍可取得账本元数据

- 路径：`cloudfunctions/ourNest/handlers/auth.handler.js:92–110`。
- 条件：用户的当前账本指针仍指向一个存在、但其已被移除的账本。
- 实际逻辑：登录按 ID 获取账本，只检查是否存在，未重新判断用户角色，即返回 `currentLedger`。
- 后果：可能继续返回账本配置和成员标识等元数据；不是继续获得全部账单。
- 反证：普通业务经 `shared/helpers.js:198–208` 的授权检查会拒绝已移除者。
- 建议：登录也重新授权，无权时选择仍有权账本或置空；保留既有历史记录归属，不把清理指针当作权限检查的替代。
- 验收：成员设为当前账本 → Owner 移除 → 成员重新登录；响应中不再包含无权账本，普通读写均拒绝。

### 5.2 高优先：快捷金额存在并发撤权窗口

- 路径：`cloudfunctions/ourNest/handlers/settings.handler.js:20–46`。
- 条件：入口授权通过后、事务读取前，成员被移除。
- 实际逻辑：事务只拒绝 `readonly`，角色为 `none` 时仍继续更新。
- 后果：已撤权者可能完成一次快捷金额修改，并取得账本返回值。
- 反证：请求开始前已无权限会被入口拒绝；账户设置接口已使用正确的 `assertWritable`。
- 建议：事务内统一断言 Owner/成员可写；保留访客只读与撤权后不可访问不变量。
- 验收：受控交错授权与移除请求，事务重读为 `none` 时不写入、不返回账本数据。

### 5.3 高优先：成员移除可能覆盖另一人刚完成的加入

- 路径：`cloudfunctions/ourNest/handlers/ledger.handler.js:236–263`，邀请事务见 `:378–435`。
- 条件：移除先读取旧数组，另一人领取邀请成功，随后移除写回旧数组。
- 后果：与移除目标无关的新成员可能被覆盖掉；令牌已绑定，关系却丢失。
- 反证：邀请使用事务、版本使用自增，但不能阻止后来的普通更新写回旧成员数组。
- 建议：事务内重读权限及最新关系，仅删除目标；保留其他成员与历史归属。
- 验收：并发加入 B 与移除 A，最终 B 仍在账本中；并发移除不同成员也不相互覆盖。

### 5.4 高优先：删除账本缺少覆盖全流程的写入围栏

- 路径：`cloudfunctions/ourNest/handlers/ledger.handler.js:465–501`，新建记录见 `handlers/record.handler.js:80–145`。
- 条件：记录阶段已清空，账本尚未删除，有权限用户又提交一笔记录或导入。
- 实际逻辑：删除阶段保存在操作日志，记录写事务只检查权限与分类迁移，不检查账本删除中状态。
- 后果：可能留下指向已删除账本的孤儿记录；从后续阶段恢复时也不会重跑已完成的记录清理。
- 反证：账本删除后重读会阻止正常写入，分类被删也可阻止部分带分类 ID 的提交，但不能覆盖整个并发窗口。
- 建议：清理前事务性标记账本删除中，相关写事务检查同一状态并形成共同冲突点；保留 Owner 权限及分阶段可恢复流程。
- 验收：删除进行时新建、编辑、导入被明确拒绝；各阶段中断重试，最终无孤儿记录；邀请、导入批次与文件的清理或保留规则单独验证。

### 5.5 中高优先：分类原子性与文档承诺不一致

- 路径：`cloudfunctions/ourNest/handlers/category.handler.js:88–97`、`cloudfunctions/ourNest/SPEC.md:20`。
- 实际逻辑：父分类改名先事务提交，子分类 `parentName` 在事务外更新；中断可能留下冗余字段不一致。
- 反证：新记录解析分类时会读取父文档，不能扩大为“全部新账单都会写错分类”。
- 建议：按现有规格原子更新，容量超限整体拒绝；保留分类 ID 与历史快照，不借此静默改写历史记录。
- 此外，默认分类修复尚未完全与版本原子提交，已有分页/分析围栏不能视为绝对稳定快照保证，见 `docs/WRITE-SAFETY.md`。

### 5.6 中优先：日期和设置入口的校验不完全一致

`validators/schemas.js:58` 对手工记录日期只检查 `YYYY-MM-DD` 格式，因此 `2025-02-29`、`2026-13-40` 这样的字符串能通过该格式判断；前端日期选择器限制不能替代服务端自然日期校验。导入已有更严格日期处理，应统一契约。

建账预算与后续预算修改也存在校验差异；建议复用同一验证器，避免“创建时允许、设置页不能保存”的状态。

金额校验本身有明确保护：`NaN`、`Infinity` 因非有限数被拒绝；`0`、负数被拒绝；`1.001` 因分位误差 `0.1 > 0.000001` 被拒绝；`100000000` 超过上限被拒绝；`1.23` 能通过金额检查。这里不能把“有日期问题”扩大为“金额完全未验证”。这是表达式核算，不是本轮执行的自动化测试。

### 5.7 中优先：快捷金额开关存在理解成本

`miniprogram/pages/record-edit/index.js:57` 显示：关闭自定义快捷金额后回退默认金额，而不是完全关闭；高铁/火车分类又优先使用固定金额。

这可能是业务意图，也可能违背用户对“开关”的理解。建议先明确开关究竟控制“启用快捷金额”还是“启用自定义金额”，再统一配置优先级；不把特定交通场景硬编码成通用产品规则。

## 6. 工程质量与长期运营能力

### 6.1 已有测试的价值与边界

当前 `package.json` 的测试入口显式列出 28 个测试文件，涵盖金额、云路由、邀请、缓存、分析契约、刷新、分类操作及组件约束等。异步迟到响应、跨会话缓存、分页冲突和失败留输入等测试方向有价值。

但大量测试依赖模拟 SDK、VM 和微信对象。它们不能证明：

- CloudBase 实际事务隔离、索引、聚合与权限规则正确。
- 双账号并发下关系、导入与分类迁移不冲突。
- iOS/Android 的 Canvas、隐藏恢复、弱网与大字体行为一致。
- 云端账单和来源文件长期保留、删除、恢复均符合预期。

`cloud:check` 只是语法检查，不是云端集成测试。本轮没有执行测试，不采用历史通过数量来证明当前版本质量。

### 6.2 性能与费用需要测量，不宜先重构

分析范围读取按页查询，普通分析并非全部受多期比较接口的 5000 条上限保护；月份趋势和年度趋势可能扩大读取范围。记录变多、多人频繁切换分析时，可能增加查询次数、延迟和云费用。

`docs/ANALYSIS-PERFORMANCE-BASELINE.md` 明确尚缺 5000/20000 条真实环境端到端测量。建议依次测：查询页数、返回字节、云端耗时、前端首屏、图表绘制、失败率和费用。

先补索引、投影和不必要查询，再按实测决定在线聚合；只有仍不达标时才引入预计算和结果缓存。不要用缓存掩盖撤权或统计不一致问题，也不需要现在拆微服务。

### 6.3 数据保护与隐私应成为正式能力

- 生产备份、恢复、迁移尚为待办；需确定备份频率、最大可接受丢失时间和恢复目标，并完成恢复演练。
- 备份不是只有文件存在，要能在隔离环境恢复并对账。
- 云存储与操作日志规则是候选配置，不随源码自动生效；需双账号和未登录客户端验证。
- 账单文件、反馈图片、头像、日志、导入标记的保留期与删除策略应分别定义。
- 应核对隐私说明、用户注销、共享数据删除范围及反馈渠道，不能只实现登录而不设计退出服务。
- 财务内容不宜直接进入埋点、错误上报或第三方 AI；性能诊断尽量只保留必要元数据。

这不是法律合规认证。本轮也未核验当前微信后台声明或实际安全规则。

### 6.4 最小工程治理比“大而全平台”更现实

建议先建立自动运行的格式、lint、单测和云端语法检查；涉及权限与导入的版本必须跑测试环境回归。少量清晰错误码、请求关联、失败率和人工告警即可起步，不必先建设复杂监控平台。

仓库没有主项目 CI 闭环的证据；工具套件自身的 CI 不能当成小程序业务 CI。生产上线前还需固定小程序与云函数版本配对、数据库变更记录及回滚步骤。

## 7. 同类产品对比：学什么，不学什么

以下选择的是有代表性的开源个人财务工具与国内/共享同类产品，不是按实时热度排序。“多用户”不自动等于“多人共享同一本账”，“同步”也不自动等于角色隔离。

### 7.1 钱迹：日常财务语义完整度

官方指南列出收支、转账还款、周期分期、债务、报销、退款、年度/月度及分类预算、资产、多账本与共享记账。

对比判断：OurNest 的微信邀请门槛低，但在退款、转账、重复支出、资产和预算深度上仍较浅。真正值得学的是“日常账务例外怎么处理”，而不是照搬每个菜单。

建议借鉴：退款与原账单关系、周期账单、搜索筛选、导出及分类预算。资产和债务管理是否引入，应取决于目标用户，而不是为了追平功能表。

来源：[钱迹指南](https://docs.qianjiapp.com/)、[共享账本](https://docs.qianjiapp.com/vip/vip_book_share.html)、[转账](https://docs.qianjiapp.com/ji-zhang-jie-mian/zhuan-zhang-cao-zuo.html)。

### 7.2 鲨鱼记账：低负担与长期习惯

官方站点介绍月预算、分类预算、定时记账、提醒、搜索和数据导出。

对比判断：OurNest 已有快捷金额与连续录入，但仍需用实际任务测量打开到保存的步骤和时间，不能仅凭存在快捷入口就宣称“几秒记一笔”。留存往往取决于少操作、找得到账和不漏账，而不是图表数量。

建议借鉴：周期支出和找账效率；不直接照搬提醒频率，也不把品牌口号中的安全保证当作审计证据。

来源：[鲨鱼记账官网](http://shayujizhang.com/)。

### 7.3 Actual Budget：预算方法与数据自主

这是开源、本地优先的个人财务工具，官方强调信封预算、多设备同步与可选端到端加密。其预算强调分配已经拥有的钱，并支持结转。

对比判断：OurNest 当前是“记录后看预算执行”，Actual 更强调“花之前分配资金”。本地优先和可选加密也是对用户数据自主的重视，但不能不加改造地移植到微信云开发架构。

建议借鉴：预算解释、结转思路、数据自主和可迁移；不据此推断它具备与 OurNest 相同的共享角色权限。

来源：[官网](https://actualbudget.org/)、[预算方法](https://actualbudget.org/docs/budgeting/)、[GitHub](https://github.com/actualbudget/actual)。

### 7.4 Firefly III：严谨账务与自动规则

这是开源自托管个人财务工具，官方介绍复式记账、多币种、预算、分类、标签、规则和独立数据导入工具。

值得特别注意：官方 FAQ 说明支持多用户，但不能由多个用户共享同一个 administration。因此不能把它当成细粒度共享账本权限的现成范本。

建议借鉴：账户之间资金流转、交易规则和数据导入的清晰模型；不照搬面向专业用户的配置复杂度，也不为轻量收支场景立即引入完整复式账务系统。

来源：[官网](https://www.firefly-iii.org/)、[GitHub](https://github.com/firefly-iii/firefly-iii)、[多用户 FAQ](https://docs.firefly-iii.org/references/faq/firefly-iii/general/)。

### 7.5 ezBookkeeping：可迁移和完整基础能力

这是开源自托管工具，官方列出多级账户与分类、多币种、周期交易、交易模板、搜索分析、图片附件和 CSV/TSV 导出等。

对比判断：它说明一款成熟的个人记账工具，价值不仅在记录和图表，还在找到记录、反复录入、批量处理及迁出。官方多用户能力不在本报告中等同于共享协作能力。

建议借鉴：可导出、模板、周期交易和筛选能力；附件和多币种可后置，避免增加存储、隐私和模型成本。

来源：[功能表](https://ezbookkeeping.mayswind.net/features/)、[导入导出](https://ezbookkeeping.mayswind.net/export_and_import/)、[GitHub](https://github.com/mayswind/ezbookkeeping)。

### 7.6 Splitwise：把“共享”与“结算”讲清楚

官方产品围绕共同支出、成员余额、分摊和结清，支持等额、指定金额等分摊方式。它解决的是“谁应承担多少、谁欠谁”，而不只是“这个月总共花了多少”。

对比判断：如果 OurNest 面向共同生活、共同规划预算，现有归属分析是合理起点；如果要服务合租或旅行 AA，当前模型还不够。

建议借鉴：共享业务概念的边界与可解释性；是否引入结算应是战略选择，而不是在现有分析页附加一个欠款数字。

来源：[官网](https://www.splitwise.com/)、[使用说明](https://kb.splitwise.com/getting-started/how-do-i-use-splitwise)、[分摊方式](https://kb.splitwise.com/balances-and-expenses/what-are-different-ways-i-can-split-an-expense)。

### 对比后的战略结论

OurNest 不适合以“功能比所有 App 多”竞争。更现实的组合是：

**小程序低门槛 + 清晰可信的收支数据 + 不误导的付款/消费归属 + 可控的共享关系。**

开源工具的完整财务模型是学习材料，不意味着应放弃现有技术栈；商业产品的宣传也不是其实现安全性的证明。

## 8. 产品经理视角：明确用户与取舍

### 8.1 优先服务谁

建议优先：

1. 想轻量管理日常收支的个人。
2. 希望共同了解开支、但不要求严格 AA 的情侣、家庭或亲密小群体。
3. 有短期共同事项、主要关注预算与支出归集的小群体。

不建议首阶段承诺完整服务：重度资产管理、专业理财、多币种跨境财务、企业报销或严格 AA 债务结算。

品牌可以温暖，但文案和业务默认值不应把所有共享关系都限定为“夫妻/家庭”。当前规格已朝这个方向演进，README 仍有较强家庭表述。

### 8.2 优先优化的四个闭环

- **开始：** 新用户能理解个人与共享的区别，完成首笔记录，不必先配置全部细节。
- **持续：** 常用记录足够快，漏记可补，导入可继续，账单找得到。
- **理解：** 每个统计能解释口径并找到组成它的明细，不把录入人当消费人。
- **离开或出错：** 能导出、纠错、处理成员关系，并在云端故障后恢复。

第四个闭环目前最弱，却最影响长期信任。

### 8.3 不建议当前优先投入

- AI 财务建议或自动上传账单给第三方模型。
- 大量皮肤、动画、徽章及装饰性图表。
- 未确定规则的 AA、借贷、资产、投资组合一起上线。
- 未测量性能就预计算全量数据、建设复杂缓存或拆分微服务。
- 为了“激活”而高频通知、打卡和分享。

AI 分类或 OCR 可以后续评估，但准确率、隐私和人工纠错闭环应先于演示效果。

## 9. 推荐改进路线与验收标准

优先级含义：P0 为保护当前数据和权限的工作；P1 为形成可信长期使用闭环；P2 为改善留存和规划；P3 为需重新确认定位的扩展。以下不作无团队规模依据的工期承诺。

### 第一阶段：P0，先让现有承诺可信

1. 修复登录撤权校验和快捷金额事务权限。
2. 将成员移除改为基于最新状态的原子更新。
3. 建立账本删除中围栏，覆盖记录、导入及相关写路径。
4. 对齐分类原子性、版本围栏与自然日期验证。
5. 在测试环境核验存储/集合规则、双账号越权、并发邀请、分类迁移和导入中断。
6. 统一文档，停止把缓存读宣传为完整离线、把轮询宣传为实时。

阶段验收：撤权不泄漏新响应，非目标成员不丢失，删除后无孤儿记录，迁移可恢复，异常日期被拒绝；每项有实际测试环境证据，而非只有模拟测试。

### 第二阶段：P1，补齐数据与关系闭环

1. 实现可对账、可迁移的用户导出；保留访客不可导出边界。
2. 建立生产备份与隔离恢复演练，明确恢复目标和负责人。
3. 先决策再实现退出、Owner 转移、角色变更与邀请撤销。
4. 定义退款/转账的统计语义，完成最常见场景而非一次做全资产系统。
5. 完成加入前确认、错误说明和导入中断后的可解释处理。
6. 明确隐私、注销、日志及文件生命周期。

阶段验收：导出与账本金额/笔数一致；备份能恢复并对账；关系变化后权限和历史展示符合已确认政策；退款与转账用例不会悄悄污染消费口径。

### 第三阶段：P2，让用户愿意持续使用

1. 用真实任务优化常用分类、最近记录复用和快捷配置优先级。
2. 补充找账能力，例如备注、标签及组合筛选；避免只有图标搜索而缺少账单搜索。
3. 评估周期账单、分类预算、历史预算及可行动的月度回顾。
4. 减少导入人工分类成本，先做来源/商户规则与批量确认，再考虑 AI。
5. 先获得 5000/20000 条真实性能和费用数据，再决定聚合、缓存或包体裁剪。
6. 建立最小 CI 和故障观察机制。

阶段验收：通过可重复任务证明时间和错误率改善；更快的分析仍能与明细对账；优化不改变既有权限与统计口径。

### 第四阶段：P3，按目标用户二选一或分期扩展

- 资产方向：稳定账户实体、余额、转账、负债和对账。
- 分账方向：参与者、分摊金额、欠款、还款及结清。

二者都能做，但都不只是多加一个字段。建议先用访谈验证需求强度，再独立规划，避免把轻量消费工具变成高门槛财务系统。

## 10. 建议如何验证“真的变好了”

### 用户任务

至少覆盖以下场景，参与者尽量包含非开发者；人数应以试验预算确定，不用小样本宣称市场结论。

- 新用户首次建账并记一笔。
- 连续补记三笔，过程中失败一次后重试。
- A 代 B 记录由 B 付款的共同消费，双方解释统计及编辑权限。
- 导入账单，识别退款和疑似重复，中断后继续。
- 查找一笔两个月前的交通支出。
- Owner 移除成员、成员重新进入；明确不可见与已缓存历史的区别。
- 导出一个月数据并与汇总对账。

### 产品指标

- 激活：首次建账与首笔有效记录完成率。
- 效率：常见记账任务的步骤、完成耗时和放弃原因。
- 共享：邀请接受、第二成员首笔记录，以及双方持续参与情况。
- 导入：完成率、重复率、人工确认负担与中断恢复成功率。
- 信任：金额差异、错误归属、无法找到账单和权限相关反馈。
- 留存：按个人/共享用户分开观察，不以“记得越多越好”作为唯一目标。

### 工程指标

接口 P50/P95、云端错误率、写入成功率、分析与明细对账、并发冲突恢复、孤儿文件/记录数量、备份恢复结果及单位活跃账本的云费用。

先建立基线再设目标，不把“3 秒”“99.9%”等没有测量基础的数字写成承诺。埋点不采集账单正文、交易对手、完整金额或成员身份等非必要敏感数据。

## 11. 文档与事实源需同步的问题

1. `goal-and-requirements.md`、README 和 `plan/PENDING.md` 仍把邀请有效期、重复领取列为未决，但实现和数据库契约已有 24 小时与绑定规则；应将仍未决的撤销等规则分开。
2. README 的“实时同步”“离线优先”“智能归类”容易使用户产生超出当前能力的预期：现状主要是缓存读取、轮询校验与人工分类确认。
3. 数据文档描述多期比较前端能力，但当前服务层未完成独立接口接入，应区分后台实现、前端可用和待验收。
4. 性能待办仍称仅完成诊断，而性能基线已有部分本地实施记录，说明进度状态已漂移。
5. 文档提到 `npm run cloud:prepare:test`，当前 npm 脚本未注册该入口，发布操作链需核对。
6. 历史性能文档中测试文件数量、测试通过数与格式检查阻断是历史证据，不代表当前结果。

建议不是扩写更多计划，而是让 README 讲现有能力、规格讲契约、待办只保留未完成事项，避免三处互相矛盾。

## 12. 最终建议

从工程师角度：**优先补授权、并发、恢复与证据，不重写架构。**

从产品经理角度：**守住轻量个人与小群体共同消费台账定位，不同时追逐资产、AA、AI 三条重路线。**

从用户角度：**先让我放心记、方便找、看得懂、拿得走，再告诉我还能分析多少维度。**

如果下一轮只做五件事，建议按顺序推进：

1. 修复撤权与并发一致性问题，并做双账号真实环境验证。
2. 完成导出、备份及恢复演练。
3. 决策并补齐共享退出、转移与角色生命周期。
4. 明确退款、转账和公共消费口径，避免统计误导。
5. 用真实用户任务改善首笔、连续录入、找账与导入负担。

**OurNest 最有机会的不是成为更庞大的记账软件，而是成为一个低门槛、关系边界清楚、数字值得信任的共同记账工具。**
