OurNest 升级优化方案｜负责人综合建议

讨论稿，不是实施授权或已验证的界面设计。 本方案综合先前静态审查及三项独立候选建议，面向首页、明细/记录详情、分析。文中顺序、文案和方案均可调整；示例数据是虚构样例，不代表真实账目。HTML 是方案阅读版，不是小程序高保真原型。涉及视觉方案时，选定方向后再做实际界面预览、评审和集成。

一、先看结论：先可信，再顺畅，最后精修

推荐采用分阶段组合方案，而不是将三位成员方案作为互斥的整包：先采用交互方案的错误恢复和权限基线，再借鉴叙事方案的信息分层，最后用 Unslop 的克制方法精修视觉。下面是建议，而非替用户作出的决定。

方案主要价值代价与取舍适合优先考虑
Unslop · 局部精修保留品牌与既有结构，压缩重复强调，重视金额和视觉节奏布局变动较小，不能单靠视觉解决数据状态和口径问题希望低扰动地改善一致性
花叔 Design · 叙事分层以账期、关键信息、详细依据组织页面，让用户循序理解需要确认哪些信息默认展开、哪些次级显示，并观察页面长度希望改善首页与分析的信息理解
UI/UX Pro Max · 任务与状态重点修复错误恢复、读屏、分页、非颜色数据路径状态与测试覆盖工作量相对较大，视觉变化可能不明显重视弱网、角色差异和可访问性
Leader · 风险分级组合先统一财务语义和可靠性，再选择性叠加视觉层级分阶段推进，不能承诺一轮完成所有高保真改造希望降低财务误读和回归风险

三份专项方案分别为 Unslop、花叔 Design、UI/UX Pro Max；原始问题和证据见 综合评估。若三份方案中的表述与现有业务相冲突，以服务端实际实现、项目规范及讨论后确认的产品口径为准。

二、共同约束：任何方案都不能突破

  • 使用现有暖红 #F0442F、浅暖背景、圆角卡片、navbar、本地图标及语义 Token；除了 tl-tabbar 不加阴影；只在规范允许之处使用渐变。复用 tl- 公共组件，不私造通用按钮/弹层/骨架；单一组件负责底部安全区。见 UI 规范。
  • Owner 可管理全部记录；共享账本成员只能编辑或删除自己录入的记录；访客无写入、导入和导出操作。隐藏入口不是安全边界，云端仍须授权。角色矩阵。
  • 本月统计来自完整查询，不以已加载分页或最近记录估算。当前周期比较同期、历史周期比较完整上期。预算是当前配置，没有历史预算档案。账户是名称，不表示真实账户余额。统计规则。
  • 付款人、消费归属与录入人不能混为一谈；多人或公共消费不自动均摊。现有 AA 数字不是一般债务或自动转账；没有离线写入、实时推送及实际导出。见 业务边界。
  • 所有错误、空数据和零值保持区别；切换账本/周期时不得显示旧上下文结果冒充新结果；不得为凑版面虚构数据。

三、页面升级方案

首页：用一眼可核对的账期概况建立信任

当前结构：账本/身份 → 预算卡 → 当月收支与结余 → 最近记录；另有加载、无账本、空和错误分支。现有模板。

建议结构（不改变既有业务顺序）：

  1. 顶部始终显示账本名称、类型/角色和明确的当前月份；切换账本期间显示加载，不混用上一账本数字。
  2. 预算卡以“剩余可用”或“已超预算”为唯一主数字，展示一次使用比例。未设置预算显示“尚未设置预算”；Owner 才提供设置动作，成员和访客不显示不可执行动作；是否显示预算本身仍遵循现有权限约束。
  3. 当月收入、支出、收支差额成组，金额语义明确。大额若压缩为“万”，仅在发生舍入时标注“约”，并保留查看精确值的可靠路径；该路径需设计和确认，不预称已存在。
  4. 最近记录标题注明“最近记录”，不暗示其为当月汇总数据源；列表保留现有可进入记录的路径及真实权限。
  5. 空态按无账本、空账本、本月无记录、只读角色区分。访客不显示“记一笔”，可在有历史记录时提供查看历史的可执行路径；所有写操作保留服务端复核。

示例文案，仅作讨论：本月预算剩余 ¥1,280.00、已使用 68%、本月暂无记录、此账本为只读。数值不来自真实用户。

取舍：只精简重复比例，不为了首屏高度隐藏关键财务信息；预算的历史语义不扩展。

明细和记录详情：让浏览、筛选、重试连续可控

当前结构：按月选择 → 全部/支出/收入筛选及范围汇总 → 日期分组 → 触底分页。只读者进入详情，其他用户进入编辑路径；成员的实际记录权限由服务端和编辑页共同保障。入口。

建议结构与状态：

  1. 月份选择和收支筛选保留；明确汇总金额/笔数对应服务端返回的范围及筛选口径，不从当前分页求总数。
  2. 首屏状态 loading → error / empty / ready；下一页单独为 idle → loadingMore → success / appendError，appendError 保留已加载记录及游标，在列表尾给“加载失败，重试”。若 RECORD_SNAPSHOT_CHANGED 则不拼接旧新数据，清晰提示并重新获取首屏。
  3. 空态区分筛选无结果、当月无数据但存在历史、账本完全无记录；只显示当前角色能够执行的动作。现有“查看最近有记录的月份”保持实际数据来源，不虚构搜索能力。
  4. 详情沿用金额、交易信息、家庭信息的分组；导入来源、长交易号、备注和历史成员可完整阅读。录入人、付款人、消费归属分别命名；未知不自动推断。
  5. 错误、空态、重试与底部操作复用公共组件。箭头/筛选控件补充微信支持的无障碍名称与状态，实测读屏和触控范围。

示例文案：本月没有符合条件的记录；加载更多失败，重试；记录已变化，已重新加载。恢复提示仅在对应操作确实成功时出现。

取舍：不新增全文搜索、批量编辑或导出。是否将可编辑用户先导向只读详情，再进入编辑，属于导航变更，需产品单独决定；当前方案不默认改路由。

分析：让结论有口径、有依据、有恢复路径

当前结构：周期及收支选择 → 概览与月报 → 趋势/明细 → 分类与家庭视角；已有分类文字列表和图表失败提示。模板。

建议结构：

  1. 顶部清楚显示账本、周期、收支方向；主数字配有该周期和对比区间说明。比较语义以实际服务端口径为准，禁止用视觉省略把同期和完整上期混成同一种。
  2. 概览只突出当前方向总额及一项有明确参照的比较；笔数、日均、收支差额继续保留，降低重复强调。周期切换成功前不把旧数据标成新周期。
  3. 趋势保留图形并提供逐项文本；周对比需显示本周、上周、日期和变化，分类保留名称、金额、比例，不依赖颜色传达唯一信息。图表初始化失败时继续显示可靠的文字数据。
  4. 分析首屏和二次请求失败均有错误说明及重试。建议默认不展示旧账期内容；若要保留旧内容，必须标记它的账本/周期并明确非当前结果，且不能被复制为新上下文。
  5. 月报提供两个待选：A 保守，仅在月度支出时提供“生活月报”；B 动态，依据当前周期、方向及个人/共享语境生成标题与内容。两者必须让屏幕预览和复制共用同一数据及语义模型；自定义周期是否提供、访客复制是否属于禁止导出需由产品和安全负责人确认，未澄清前不扩大访客权限。
  6. AA 采用安全底线：无法从现有数据证明“参与者、共同费用、等额分摊、未结算”等假设时，不展示确定性应付款或“结清”文案。可改为仅展示付款差异及说明，或者经产品确认并具备数据证据后提供明确假设下的估算；不新增转账和自动结算能力。

示例文案：本期支出、与上期同期相比（仅当前周期且适用时）、数据加载失败，重试、付款差异不代表实际应付款。

取舍：动态摘要比仅保留月度支出覆盖面广，但增加语义组合与测试成本；AA 从“结算建议”降为“付款差异”更稳健，但会减少直接操作感。

四、实施路径与门禁（需获得后续实施授权）

阶段内容依赖/改动范围验收门禁
0 事实确认微信开发者工具复现二次失败、分页失败和访客空态；盘点 AA 服务端输入，产品确认摘要口径测试账本、角色和非生产数据记录复现步骤、版本、预期/实际；未复现的问题保留待查，不直接标已修
1 可信与权限分析错误状态、摘要文案、AA 安全表达、只读入口分析模板/逻辑及视图模型、首页/明细模板、相关测试；必要时再评估服务端契约组合文案与数据一致；所有错误可恢复；访客无写入口且云端仍拒绝越权
2 连续任务主明细及分析下钻的追加失败与快照冲突，公共按钮替换明细组件、筛选页、组件测试；沿用游标与快照机制追加失败不丢已有内容；重复重试不重复/遗漏；冲突后不混合快照
3 可读与精修无障碍名称/状态、趋势文本对照、预算去重、大额近似标识、局部层级图表、样式、模板、文本模型；真实机型与读屏检查图表核心数据有文字路径；大字长文本不截断；精确与近似不混淆

工作量只作相对判断：阶段 0 取决于环境准备；阶段 1、2 为中等以上风险（财务语义、异步状态和权限）；阶段 3 的设备验证工作量随机型与读屏覆盖增加。实施中如需改接口、字段或权限，必须同步调用方、数据文档和测试，并在测试环境准备回滚；本轮方案不要求修改云端契约。

五、验证矩阵与完成标准

  • 数据：周/月/年、当前与历史、自定义 × 收入/支出 × 个人/共享；预览、复制和服务端实际聚合逐项一致。历史预算不被误称为当时配置。
  • 角色：Owner、成员、访客 × 自己/他人记录 × 空/有历史/筛选空；访客不能通过构造请求写入，成员不能修改他人记录。
  • 故障与竞态：首次失败、首次成功后二次失败、分页第二页失败、快照冲突、网络恢复、快速切账本/周期；断言当前视图不出现旧请求数据。
  • 设备：微信开发者工具和 iOS/Android 真机，窄屏、大字、长账本/成员/分类名、大金额、安全区、弹层、图表；系统读屏验证名称、状态、焦点与返回。无真实账单和个人隐私进入测试截图。
  • 工程：实施后按 回归清单 执行 npm run verify、npm run ui:check；关键视觉变更执行 npm run visual:check，分析专项执行 npm run visual:analysis:check。区分自动化、开发者工具、真机及云环境证据，不用本地通过推导发布通过。

六、请用户比较后决定

  1. 视觉力度：保持现有布局做局部精修，还是允许调整各模块的信息层级与折叠方式？哪些内容必须首屏保留？
  2. 摘要：只保留月度支出报告（A），还是生成随周期/收支/账本变化的摘要（B）？自定义周期是否包含？
  3. 家庭付款：优先只展示付款差异，还是在满足明确数据条件后提供带假设的两人估算？是否允许复制该说明？
  4. 分析失败：默认清空旧数据并提供重试，还是保留带醒目标记的旧账期结果？
  5. 记录路径：继续现有的可编辑用户直达编辑，还是另行设计“先详情再编辑”？这不是本方案默认变更。
  6. 实施边界：先只做阶段 0–1，还是在确认方案后一次规划至阶段 3？部署、生产数据和发布不包含在本次授权中。
