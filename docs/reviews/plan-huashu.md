# 候选方案：一条可追溯的家庭账务叙事

**状态：供比较决策的文字候选，不是已选定方案或视觉原型。** 本方案从“先看本月处境 → 找到具体记录 → 理解变化及口径”的使用顺序组织信息；不以增加图表、卡片或新风格作为升级目标。适用于希望日常快速掌握账务、遇到疑问又能回到原始记录的用户。这里的文案和金额均为说明性示例，不代表实际用户数据、已验证指标或既定业务规则。

## 决策定位与差异

- **主张**：首页回答“现在怎样”，明细回答“发生了什么”，分析回答“为什么变化”；每个结论尽可能提供相同账本、相同区间、相同收支方向的追溯路径。家庭付款、消费归属、录入人是不同维度，不合并为含糊的“贡献”。
- **与其他可能方案的区分维度**：相对以首页功能入口密度为主的方案，本方案优先一条主信息和可追溯关系；相对以图表丰富度为主的分析方案，优先标注口径和数据表替代；相对全新品牌视觉改版，本方案复用现有页面与设计系统。这里仅说明比较轴，不假称已看过或评价其他候选方案。
- **权衡**：首页少展示平级模块、分析把深入内容后置，可能增加访问某些次要信息的点击或滚动；明确身份与口径也会增加少量文字。需用实际使用反馈确认。
- **依据**：目前首页、明细和分析为同一容器下的 tab（[页面容器](../../miniprogram/pages/index/index.wxml#L9-L31)）；已有家庭付款/消费/录入维度（[分析模板](../../miniprogram/components/tl-tab-analysis/index.wxml#L468-L565)）。问题与未验证边界详见 [专项评审](./huashu-review.md)。
- **视觉边界**：延续暖红 `#F0442F`、浅暖背景、圆角卡片、自定义 navbar、现有本地图标和语义 Token；优先公共 `tl-` 组件，不额外引入阴影、非规范渐变或页面私有通用控件。唯一底部安全区责任者、状态互斥及图表生命周期遵循 [UI 规范](../UI-GUIDELINES.md#L5-L17)。无需制作方向稿或新视觉设计。

## 结构提案一：首页「本月处境 → 最近发生」

### 当前与候选

当前根据账本和预算状态分支显示本月预算、收支/结余、最近十笔等；无账本或无记录时有对应空态（[首页模板](../../miniprogram/components/tl-tab-home/index.wxml#L4-L111)、[就绪内容](../../miniprogram/components/tl-tab-home/index.wxml#L112-L205)）。

候选结构从上到下：

1. **上下文**：保留当前账本切换和本月标识；账本名称、类型及只读状态让用户能判断当前数据属于哪里。避免以“家庭”笼统称呼个人账本。
2. **本月概览**：统一呈现收入、支出、结余，明确结余为收入减支出；预算已启用时预算块紧邻概览，突出剩余/超支、已支出和预算总额；未启用时只对有管理权限者提供设置入口。保持现有预算计算，不在前端臆造结论。
3. **最近记录**：保留最近记录及“全部”，明确是账本最近 10 笔而非必然属于本月。点击保留对应权限的详情路径；“全部”进入明细时传达当前账本和默认月份，跨月时不能让用户误以为已精准筛选该记录。
4. **操作**：中央记账入口继续由现有 tabbar 承担；空态仅对可写用户提供可执行的记账入口，不新增第二个固定底栏。

**示例（虚构）**：`旅行账本 · 共享 · 6月` → `收入 ¥8,000 / 支出 ¥5,200 / 结余 ¥2,800` → `预算 ¥6,000 · 已用 ¥5,200 · 剩余 ¥800` → `最近记录（账本最近10笔）`。金额若为舍入展示，显示 `≈`，且用户能进入对应明细查看精确值；实际是否提供精确汇总入口需确认。首页金额当前存在万元单位舍入（[格式化](../../miniprogram/components/tl-tab-home/index.js#L17-L20)）。

**状态与权限**：加载仅显示骨架；加载失败显示错误和重试，不用零值冒充成功；无账本显示创建入口（具体权限以登录/账本规则为准）；有账本但无历史记录与本月无记录文案分开，后者仍可查看历史；访客看到只读说明，不提供记账、预算设置、导入或导出。预算仅 Owner 可管理，成员和访客展示什么以现有服务端授权及产品决定为准，不将隐藏按钮当安全边界。现有访客空态仍展示写入按钮的条件风险见 [评审](./huashu-review.md#p2--访客空态展示不可执行的记一笔)。

## 结构提案二：明细/详情「列表定位 → 单笔核对」

### 明细列表

当前结构是月份切换、全部/支出/收入、月汇总、按日期分组列表及分页（[明细模板](../../miniprogram/components/tl-tab-records/index.wxml#L1-L95)）。候选保留此顺序，但明确三层语义：

1. **筛选上下文**：账本、月份与收支方向始终可辨；方向改变时标明汇总是否随筛选变化，具体口径以服务端返回契约核实，不将月汇总称为筛选汇总而未经验证。
2. **范围摘要**：一行收入、支出、笔数；摘要与列表数据范围一致时直说范围，不一致则各自标注。大额和长名称不能裁去关键数字或正负号。
3. **日期组与单笔**：保留日期、每日收支合计；每笔优先分类、金额及收支符号，其次时间、记录人、备注。连续追加时显示加载进度，结尾明确无更多；追加失败保留已显示记录，在尾部提供“加载失败，重试”。

**示例（虚构）**：`6月 · 支出` → `当前范围：支出 ¥320，共 2 笔`（是否可得和口径须核实）→ `6月12日 · 支 ¥320` → `餐饮  -¥120 / 12:30 · 小林`。筛选为空时说“本月没有支出”，不把它误说成账本没有任何记录；本月无记录但有历史时保留已有“查看最近有记录月份”能力（[当前空态](../../miniprogram/components/tl-tab-records/index.wxml#L88-L94)）。

首屏失败使用公共错误态和重试；追加失败只影响尾部，不遮盖已有列表；快照变化应说明“记录已变化，正在重新加载”，重建范围后恢复可见一致性，不拼接不同快照。现有分页采用 `date,id` 游标、默认 30、上限 50；不以视觉方案改变协议或伪造汇总。

### 详情与分析下钻

当前只读详情按金额、交易信息、家庭记录组织（[详情](../../miniprogram/pages/record-detail/index.wxml#L12-L80)）；首页和明细按账本只读状态分别进入只读详情或编辑页面（[首页跳转](../../miniprogram/components/tl-tab-home/index.js#L471-L475)、[明细跳转](../../miniprogram/components/tl-tab-records/index.js#L435-L439)）。候选统一**阅读顺序**而不预设必须合并路由：

1. 顶部固定语义为收支类型、分类、带符号金额、发生日期；
2. “交易”显示账本、账户和必要来源信息；导入交易号/批次仍可核查，但可放在次要信息区，不能无提示删除；
3. “家庭记录”清楚区分记录人、付款人、消费归属、收入归属；仅在业务适用且数据存在时显示，历史成员保留历史身份而不冒充当前用户；
4. 备注和标签保留；可编辑记录显示明确的编辑/删除操作，只读或无权操作他人记录时为阅读态，是否需要从编辑页拆出阅读页需产品决策。返回列表时保留筛选和滚动位置作为目标，需评估现有路由生命周期。

分析下钻页始终带来源筛选上下文：账本、区间（注明结束日期排他或转换为清晰的自然日展示）、收入/支出和分类/账户/成员维度。现有下钻使用“起至…前”（[参数与范围](../../miniprogram/pages/record-filtered/index.js#L29-L63)）；展示改变不意味着改变查询边界。追加失败保留列表并单独重试，既有 `snapshotRevision` 恢复流程需保留（[分页逻辑](../../miniprogram/pages/record-filtered/index.js#L82-L145)）。

**权限边界**：Owner 可管理全部记录；共享账本成员仅可编辑或删除自己记录；访客只读且不允许导入导出。对成员查看他人记录，需确认编辑页实际呈现与服务端逐条授权，不凭账本级 `readonly` 推断记录级权限；变更权限前后的在途请求也要重新判定。任何入口隐藏只是体验控制，云端仍为唯一授权边界。

## 结构提案三：分析「结论 → 组成 → 证据」

### 当前与候选

当前分析有周、月、年、自定义及收入/支出切换；常规周期有概览、趋势、排行、分类、账户和家庭维度，图形有部分文本替代（[分析模板](../../miniprogram/components/tl-tab-analysis/index.wxml#L1-L55)、[概览及趋势](../../miniprogram/components/tl-tab-analysis/index.wxml#L71-L185)、[分类及账户](../../miniprogram/components/tl-tab-analysis/index.wxml#L242-L316)）。

候选顺序：

1. **分析上下文**：账本、周期、具体范围、收入/支出选择并列呈现；切换后先进入加载，再以新的上下文展示结果。自定义区间清晰显示选中起止日、最大范围和比较方式；内部结束日期排他不应造成视觉少一天的误解。
2. **本期结论**：一项本期收入或支出总额、笔数、日均，附收入/支出/结余；比较值标明对比哪一期、是否同期或未结束。不可得时写“暂无可比数据”，不以 0、持平或事实性叙述替代缺失数据。是否具备“不可比”标记需核查接口。
3. **组成**：先显示分类及占比，再按需查看账户；金额、百分比和笔数同时呈现，不依赖颜色。点击分类或账户先提供数据预览，再到完整匹配记录，明确相同过滤条件。
4. **变化与证据**：趋势图保留，并提供可展开的文本明细；柱体、日期或趋势行可下钻相同范围，图表失败仍能读数据表。月日历和排行属于进一步探索，保留但不要求首屏全部展开；折叠状态及默认项需用户确认。
5. **共享账本解释**：仅在服务端返回适用维度时显示付款人、消费归属、录入人，并分别说明含义，不能用付款金额替代应承担金额。

**示例（虚构）**：`6月 · 支出` → `本期 ¥5,200 / 24笔 / 日均 ¥173.33` → `餐饮 ¥2,000，占 38.5%` → `查看餐饮的 8 笔`。数字仅说明层级，不证明仓库中的任何统计口径或数据。周/月/年若用于“生活月报”，候选优先限制为月度支出且匹配账本语义；若产品希望跨周期、跨收支使用，则改为动态的“本期报告”，并同步所有弹层、复制文本和数值。实际选择待决，不能把收入标为支出（[原问题](./huashu-review.md#p1--生活月报的周期和收支标题可能误导)）。

**AA 安全边界**：本方案不默认提供应转账金额。先确认两人、共同费用、等额分摊、历史已结算项目等数据与业务规则均可验证；不满足或信息不足时仅显示付款/消费统计与“不构成结算建议”，不生成具体转账数。若未来获批，必须说明计算前提、适用记录与排除项，且复制文本同口径，不能说已经结清。当前实现只取前两位付款人并以差额除二（[现有计算](../../miniprogram/components/tl-tab-analysis/dashboard.js#L84-L107)），这不能证明实际债务。

**状态与一致性**：首次加载、空账本、范围内无记录、失败、成功互斥；已成功后的刷新失败也有可见错误和重试。跨账本/范围切换时不能显示旧值作为新范围结果；图表节点的挂载可与可见状态分离，但应保证数据隔离及生命周期正确。局部图表失败保留文字数据及局部重试；无该方向记录不应伪造趋势或结论。分析二次失败风险为静态发现，须先复现（[评审](./huashu-review.md#p1--分析刷新失败后可能没有错误或重试入口)）。

## 可验收条件（候选，不代表已通过）

- **上下文与数值**：每个首页汇总、分析汇总和下钻列表能看出账本、时间范围和方向；收入、支出、结余与服务端数据一致，近似数明确标识；月报/复制内容的周期、方向和数值一致。
- **权限**：Owner、成员查看本人/他人记录、访客分别验证可见入口与服务端拒绝；访客无写入、导入、导出入口；权限变更后旧页面和请求不能继续提供未授权操作。
- **状态**：无账本、空账本、本月空但历史非空、筛选空、首次错误、成功后刷新错误、图表单独错误均有正确且可理解的状态；追加失败保留已加载记录，可重试；切账本/范围的旧响应不得覆盖当前结果。
- **追溯**：从分类、账户、日期和成员维度下钻后，查询的账本、半开时间范围、类型与筛选条件不变，汇总和明细口径可解释；空结果与失败不混淆。
- **业务安全**：无可靠前提时不展示具体 AA 应转账数字；不存在虚构成员、分类、账户或财务结论；记录历史归属不因人员退出而丢失。
- **体验与工程**：使用公共组件与现有 token；真机检查长账本名、长备注、大数、字号、对比度、触控热区、安全区、键盘与读屏。实施后按影响范围运行自动检查、`npm run ui:check`、适用的 `npm run visual:check` / `npm run visual:analysis:check`，并依据 [回归清单](../REGRESSION.md) 测试；视觉基线不能未经确认直接更新。

## 需决策与未验证事项

1. 首页预算与收支的先后：用户主要看剩余额度还是本月结余？是否需要精确金额入口及如何呈现？
2. 明细摘要在类型筛选后应展示全月还是筛选范围？服务端实际返回及空态含义需在测试环境核实。
3. 详情是否始终先阅读再编辑，还是保留可写用户直接进入编辑页？如何保证成员查看他人记录仅为只读？
4. 分析的“生活月报”仅限月度支出，还是推广为随上下文变化的报告？个人账本是否使用“家庭”措辞？复制是否属于受访客限制的导出，需产品与安全规则明确，未获确认前采用保守限制。
5. AA 的共同开支、多人、既往结算、消费归属和舍入规则是否有可核验的事实源？没有就不提供具体结算金额。
6. 图表默认展开、日历和排行位置、跨页返回滚动恢复能否在真实设备上支持？分析收入/支出切换、日均及同期比较的服务端口径还需验证。

本方案基于静态源码和规范，不是运行或真机结论；未调用真实账务、未运行测试、未修改产品代码。实施前须复现报告中的条件性风险并确认业务口径。
