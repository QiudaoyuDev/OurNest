首页、明细与分析页 Unslop 升级候选方案

定位与边界

本稿供产品与设计选择，不是实施方案或已批准的改版。依据当前工作区静态代码与 专项审查，覆盖首页、明细列表及筛选明细、记录详情、分析页；工作区可能包含既有未提交改动。未运行微信开发者工具、截图、真机或测试；所有视觉密度、可读性和交互效果均未经实测，不能据此宣称视觉问题已经复现或修复。

Unslop 判断为局部精修候选，保留现有功能及区块顺序，不为改版而改版。以下示例金额、日期仅为说明展示关系的虚构样例，不是产品数据或承诺。涉及统计口径、权限和行为的建议实施前必须核对服务端与测试，不凭文案推断能力。

设计方向（供选择）

  • 产品：个人及家庭记录收支、预算和共享账务的小程序。
  • 性格：温暖、可信、清楚。
  • 世界：日常家庭账本；用真实账期和数据组织内容，而非装饰性素材。
  • 重点：首页预算剩余与分析中的真实走势，各页面让一个主要财务信息成为阅读锚点。
  • 标识细节：一致呈现账期、收支方向和成员归属，不虚构新品牌符号。

品牌与规范不可突破：保留 OurNest、暖红 #F0442F、浅暖背景、现有圆角卡片、navbar、现有字体及本地 ri-icon 风格；复用语义 Token 与 tl- 组件；除 tl-tabbar 外不加阴影，渐变只用于规范允许的背景、Tabbar 中央操作与骨架。小程序以现有 rpx 和设备表现为准，不生硬套用桌面 4px 栅格。依据：UI 规范。

候选路线与取舍

路线内容优点代价与建议
A｜准确性优先修正报告口径与只读入口；明细按钮复用公共组件改动最小，先解决确定的语义及权限入口问题阅读层级与图表风险仍留待后续；适合紧急修正
B｜局部精修（推荐讨论）在 A 上整理预算重复、分析重复与图表可读性，轻调明细和详情排版保持功能与区块顺序，兼顾准确性和阅读体验需多状态视觉基线与真机确认，图表调整存在数据区分风险
C｜强化数据表达B 之上进一步探索图表布局和视觉层级数据阅读锚点更鲜明改动和验证成本更大，尚无实机证据证明必要；仅作为独立设计探索，不视为本次承诺

以下按 B 展开；A 可单独选择。优先级表示建议先后，不代表已批准开发。

P1｜跨页口径与只读安全入口

分析报告：周期和方向与数据一致

  • 现状 → 候选：周/月/年概览均显示“生活月报”，弹层与复制内容固定称“家庭总支出/家庭支出”，实际金额来自当前分析方向。改为基于真实周期和方向命名，个人账本避免强制称“家庭”；或仅在月度支出满足既有口径时保留“生活月报”，其他组合用中性名称。保留报告入口和既有复制能力，不新增导出。
  • 文案示例：周度收入为“本周收支报告 / 本周收入 ¥8,000.00”；月度支出为“本月收支报告 / 本月支出 ¥3,200.00”。标题、预览、复制文本的实际账期范围、方向和数值必须相同；比较文案须注明比较对象。共享账本与个人账本都以事实为准，不推断共同承担。
  • 状态与权限：无可用汇总不展示伪数据；加载及错误不能复制旧账期结果。访客不能出现导出操作；复制功能是否被产品定义为导出须先确认，在规则未澄清前不扩大访客权限。客户端隐藏不替代服务端授权。
  • 业务边界：不得把收入称支出、周或年称月；不要更改总额、结余、日均或比较计算口径，不根据两人付款差额声称应付款或完成结算。
  • 涉及代码：分析模板、报告弹层、复制文本；可能涉及对应数据映射与测试，实施时核对调用链。
  • 验收 / 风险：周、月、年 × 收入、支出 × 个人、共享账本逐一对照预览和复制文本及实际汇总；切换范围中断请求、错误与空态不得复用旧结果。命名调整可能影响用户对现有“月报”的认知，需产品确认。

首页及明细：只读空态去除写入口

  • 现状 → 候选：空态无条件显示“记一笔”，处理器遇 readonly 才提示返回。访客空态只显示“本月暂无记录”及可用的阅读路径；有权限时保留“记一笔”。明细已有的“查看最近有记录的月份”在满足原条件时保留，不把它描述为新能力。
  • 状态与权限：无账本、空月份、筛选无结果分别提供准确提示；访客不显示记账、导入、导出入口，Owner/成员依既有权限展示操作。其他写操作同样遵循服务端角色与记录归属；保留客户端防御及服务端校验，不改变权限模型。
  • 涉及代码：首页空态、首页只读拦截、明细空态、明细只读拦截。
  • 验收 / 风险：访客、成员、Owner 分别检查空账本、空月份、类型筛选为空；访客没有写入入口，成员/Owner 可走原授权路径，直接调用仍由服务端拒绝越权。避免把空筛选误说成整个账本无记录。

P2｜首页：预算主次更清楚

  • 现状信息结构：月份与账本 → 空态或预算卡 → 收支/结余 → 最近记录；无预算或空账本的分支不同。预算卡的状态标签与右侧徽标重复显示使用比例。模板、正常态。
  • 候选结构：保持各分支既有区块及顺序；预算卡内部保留“本月预算”→ 剩余可用或已超支金额 → 一次使用比例及进度 → 总预算、已支出 → 原有明细/设置入口。超支状态以文字明确，不单靠颜色；只保留一次比例，不隐藏超支金额。
  • 示例文案：“本月预算”“剩余可用 ¥1,200.00”“已使用 70%”“总预算 ¥4,000.00 / 已支出 ¥2,800.00”；超支时为“已超支 ¥200.00”，进度与实际金额计算以既有数据为准，不以示例数字限定精度或阈值。
  • 状态/权限：未启用预算保留现有说明；只有具备 canManageBudget 的角色显示设置，访客只看允许的内容。加载、错误、空和正常态互斥，切换账本期间不显示上一个账本的数字。
  • 涉及代码：首页模板、首页正常态模板、首页样式、预算进度组件；仅在验证一致时考虑提取两套重复模板。
  • 验收 / 风险：分别检查未开启、0%、接近阈值、100%、超支、大金额及长账本名；使用比例只出现一次且进度/金额对应。紧凑金额与完整金额的取舍须避免失去必要精度，空态和正常态不能因模板合并改变功能。

P2｜明细及详情：清晰、可读、组件一致

  • 明细现状 → 候选：月份切换 → 全部/支出/收入及本月汇总 → 按日分组的流水与分页；维持顺序和筛选语义。行内继续以分类、金额为主，时间、成员与备注为次；日期小计保持收支标签及金额对齐，不通过颜色单独传达方向。错误重试与空态按钮改用既有 tl-button 变体，不另建私有通用按钮。明细模板、私有按钮样式、筛选明细公共按钮。
  • 详情现状 → 候选：类型/分类、金额与时间 → 交易信息 → 家庭记录及备注标签；保留字段、顺序及条件显示，仅核对长值换行、数值对齐与视觉层级。收入归属仅共享收入显示，付款人与消费归属仅共享支出显示；来源、交易号和导入批次仅在已有字段时显示，不新增编辑、删除或复制功能。详情模板、映射与默认值。
  • 示例文案：错误“明细加载失败 / 重新加载”；空月份“本月暂无记录”；详情“支出 / 餐饮”“记录人”“付款人”，以真实字段为准，不凭缺失数据补造姓名。
  • 状态/权限：加载骨架、错误重试、空态与数据态互斥；分页加载中与到底提示保留。详情无记录或请求失败显示错误而非伪造记录；访客只读，共享账本成员只能操作自己的记录，Owner 可管理全部记录，入口及服务端都须遵守现有规则。
  • 验收 / 风险：测筛选切换、跨月及加载更多；长分类/备注/成员名、超大金额、来源号换行，内容不截断或重叠。公共按钮替换须核对事件绑定、禁用和触控区域；不修改分页游标、排序或业务字段。

P2｜分析：保留数据，降低重复与阅读负担

  • 现状信息结构：周期/收支选择 → 概览（总额、笔数、日均、报告、结余、对比、叙述、家庭付款和收入/支出/结余）→ 小结走势等 → 分类、账户及共享支出；自定义范围有独立路径。分析模板。
  • 候选结构：保留周期、方向、既有区块及顺序；概览以“范围 · 方向 / 当前总额”为主，笔数日均次之；只保留一处结余数值，保留收入、支出及既有报告、对比和家庭付款内容。走势作为数据重点，分类及账户数据仍按原路径可达。先比较样机再决定叙述与徽标的弱化方式，不删除业务内容。
  • 示例文案：“本月 · 支出”“¥3,200.00”“共 18 笔 · 日均 ¥106.67”“较上月减少 12%”；比较仅在实际有可比较数据及口径成立时展示，不把单期增长称持续增长，不对正结余作未经验证的健康评价。叙述生成。
  • 图表：先实测自定义走势轴与图例；如难读，优先减少标签密度并按设备调大文字，不虚构数据。分类名称、数值和占比应可独立理解，不只靠颜色；哈希分类色可能碰撞，若改变映射应保证图表和列表一致且避免破坏语义色。图表字号及颜色、趋势配置、分类列表。
  • 状态/权限：初次加载、错误、无账本、空范围和就绪应可区分；切换周期或账本时不得将旧数据误标为新范围。已有温和刷新策略是否符合互斥规范须在实现前检查，不能仅靠隐藏样式证明。报告权限按前述待确认边界处理。
  • 验收 / 风险：周/月/年/自定义 × 收支 × 空/单笔/多分类/大金额；核对最高值、日均、结余、对比及点击数据的范围与真实数据一致。测试长标签、多分类同色、窄屏、大字号、加载错误与在途响应；不通过删数据解决密度，不擅自改统计或共享结算规则。

全局验收与实施顺序

  1. 选定 A 或 B，先确认报告复制的访客权限、周期命名和信息取舍；所有建议目前未落地。
  2. 实施时先解决 P1 语义及只读入口，再做 P2 组件与层级；各步骤保留既有服务端鉴权、分页及金额契约，不做数据迁移。
  3. 补充受影响的自动化测试与权限/口径回归；按项目要求运行 npm run verify、npm run ui:check，关键视觉变更再运行 npm run visual:check 和 npm run visual:analysis:check，基线只能在人工确认后更新。
  4. 在微信开发者工具及真机检查常规/窄屏、大字号、安全区、键盘/弹层、长文本与对比度，记录实际设备和结果；检查 Owner、成员、访客及个人/共享账本。视觉命令和手工回归要求见 UI 规范 和 回归清单。

待决问题

  1. 现有报告复制在产品与权限规则中是否属于访客禁止的导出？应由产品与安全负责人明确后决定入口。
  2. 周、月、年是否统一称“收支报告”，还是仅月度支出保留“生活月报”？需确认既有用户习惯与分享文案。
  3. 概览结余保留在顶部徽标还是三项汇总？保留哪处以真实屏幕和使用反馈决定。
  4. 分类同色是否在目标设备造成歧义？先验证名称、比例及图表可读性，再决定是否调整颜色分配。
  5. 成员退出后的历史姓名与缺失字段如何呈现，应遵循现有服务端数据及隐私规则；此方案不改变字段契约。
